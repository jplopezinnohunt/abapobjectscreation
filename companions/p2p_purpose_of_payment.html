The separate note-to-payee mechanism (SWIFT :70)

Y_FI_PAYMEDIUM_NOTE_TO_PAYEE reads YVENDOR_PAYM_REF by (BUKRS, LIFNR, BLART) and writes FPAYP-ZREF01. With no row it falls back to a format chosen by FPAYHX-PREFTYP: 'SAMPLE 01' → No.<xblnr>/<bldat>; 'SAP SEPA' → /INV/<xblnr> <bldat>. Y_FI_PAYMEDIUM_06 and _DMEE_30 read the same table.

Brain correction. The sap_payment_bcm_agent skill states this FM builds EXO//reason//XBLNR// from REGUP-BLART. The string EXO appears in none of the ten recovered sources. That text came from a specification, not from the code. Where EXO// is actually produced is still unknown — likely a DMEE tree constant.

Scope — SocGen only, by written specification

PPC functional spec v2.0 (M. Spronk), page 16: the development is only for the XML file of Société Générale. Citibank payments do not carry PPC. Making a purpose code mandatory for a Citi-routed country is a new development, not a configuration change. (claim 267)

How you make a country mandatory — the change spec

One row type is the switch. U917 blocks the posting when the vendor's bank country has any YTFI_PPC_STRUC row with PPC_CODE = 'PPC_VAR' or 'PPC_DESCR'. Everything else makes the code usable and renderable; that row makes it mandatory.

Only O uses PPC_VAR — the clerk's code. Payroll and replenishment are fixed, because the purpose is known in advance. PPC_VAR on the O rows is what makes the country mandatory.

Two caveats that decide whether it is worth doing. (1) Capture is enforced for company code UNES only — the 387 Egypt-bank-settling lines are all UNES, so for the population Citi binds this works, but 1,720 lines in ICTP/UIL/IIEP/UIS/UBO stay uncontrolled. (2) The rendering half is moot for this path: Egypt payments leave as pre-numbered cheques with no SAP file. Adding the rows still buys the capture — the clerk is forced to state a purpose and the value sits on the document for whoever fills the bank portal.
