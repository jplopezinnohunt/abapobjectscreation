1 · How you make a country mandatory

The switch is a single row type. U917 blocks the posting when the vendor's bank country has any row in YTFI_PPC_STRUC whose PPC_CODE is PPC_VAR or PPC_DESCR. Nothing else switches it on — not T015L, not YTFI_PPC_TAG, not the payment method. 
* YRGGBS00 : 1547-1590 — the whole enforcement, in one SELECT
SELECT SINGLE * FROM ytfi_ppc_struc
  WHERE land1 = @lv_banks                          " LFBK-BANKS, the vendor's BANK country
    AND ( ppc_code = 'PPC_VAR' OR ppc_code = 'PPC_DESCR' ).
IF sy-subrc = 0. b_result = b_false. ENDIF.        " posting BLOCKED

Note what it keys on: LFBK-BANKS, the country of the vendor's bank account. Not LFA1-LAND1, the vendor's address. A vendor domiciled in India who banks in Singapore is not affected; a vendor anywhere who banks in Egypt is.

The trap in T015L. ZWCK1 is not a description field. It is two fields in one, split at the first space. JO0 = "206 Overseas Incoming Salaries" means the bank code is 206 and the text is Overseas Incoming Salaries. Get the space wrong and the bank receives a mangled code.

4 · The exception tables — how a control gets switched off per user

YXUSER is a per-user bypass, and it is bigger than the documentation said. Every gated routine opens with SELECT SINGLE * FROM yxuser WHERE xtype = '<x>' AND uname = sy-uname followed by CHECK sy-subrc <> 0 — a row in YXUSER means skip this entire routine for this user. 5 · Egypt — the PPC code structure, researched

What Citi actually asked for

The notice (12 Jul 2026, effective 5 Sep 2026) says to populate the Purpose of Payment in the Transaction Details / Payment Details field, or SWIFT Field 70, and that "the PoP should clearly and concisely describe the reason for the payment". Its examples are sentences, not codes: "Payment for goods received under Invoice 12345", "Service fees for consulting work", "Salary payment". It closes with "ensure the description is specific enough to convey the nature of the transaction".
The notice names the field, and that decides the configuration. "populate the Purpose of Payment in the Transaction Details / Payment Details field, or SWIFT Field 70". SWIFT :70 is Remittance Information, and in ISO 20022 that is RmtInf/Ustrd — nothing else. So Egypt's YTFI_PPC_TAG row is USTRD, the family BH/ID/IN/JO/MA/MY/PH already use. It is not INSTRINF: that renders InstrForCdtrAgt, the SWIFT :72 instruction to the account-with institution, which is what AE and CN use and is a different field entirely. One sentence in the notice removes the only structural choice there was.
And there is no code list in the request. Egypt is therefore not an AE/JO-style country where the bank dictates numeric codes. The load-bearing block is PPC_DESCR (the narrative), not PPC_VAR — and Citi's own example ties the description to the invoice, which is exactly what PAY_FIELD FPAYP-XBLNR emits.
Scope, also from the opening sentence: the requirement covers "all Real Time Gross Settlement (RTGS) and Cross Border Funds Transfers (CBFT)" for payments "destined for or originating within Egypt". RTGS is the domestic Egyptian rail and CBFT the cross-border one, so it binds both the EGP01 local account and the USD01 cross-border one — the configuration is per country, not per currency, which is what YTFI_PPC_STRUC.LAND1 already keys on.

6 · Two limits that decide the value of doing it

Enforcement reaches one company code of nine. U917 is step 012 of validation UNES, and OB28 assigns that validation to UNES only. ICTP (4 steps), IIEP (2), UBO (3), UIL (1), UIS run their own rule bodies; IBE, ICBA and MGIE have no validation assigned at all. claim 485
For Egypt this is survivable: all 387 lines that settle at an Egyptian bank are UNES. But 1,720 lines to Egypt-domiciled payees sit in the other institutes with no capture control.
The rendering half does not apply to this payment path. Measured in P01: T042E UNES/method 3 → ZFORN='Y110_PRENUM_CHCK' with no PMW; T042Z FR/3 = "Manual cheque (Pre-Numbered)", PROGN=RFFOUS_C, XSCHK='X'; and for the five most recent Egypt runs there is no REGUT row and no PAYR row — no payment file is produced. claim 488

Citi's requirement binds instructions submitted through Citi channels; a pre-numbered cheque is not one. Configuring Egypt still buys the capture — the clerk is forced to state a purpose at invoice entry and the value sits on the document for whoever fills the bank portal — but the instruction itself is issued outside SAP, and populating it there is a process change, not a development.
