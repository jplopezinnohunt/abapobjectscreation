BCM Bank Signatory — Companion

How payment signing/approval works in SAP Bank Communication Management (UNESCO) and how to resolve a signatory-panel change. All data is read live from P01 via RFC — not from screenshots. P01 is read-only for the agent; DBS executes changes in OOCU_RESP. · v2 · 2026-06-18 · origin: INC-000011781.

🔍 AUDIT OBSERVATION — the payment block is set by a HIDDEN direct database write (that is why nobody sees how it changes)
While process-mapping BCM we found an undocumented direct-modification path that explains why nobody can see how a payment block gets set or cleared: the custom BOR method YBSEG.ZCREATEPAYMENTBLOCKWF (subtype of BSEG, prog YBSEG_REL) sets the block with a raw SQL UPDATE bseg / bsik SET zlspr='W' straight on the document — invoked from the FI Release-for-Payment workflow WS90000003 (a document-level gate before F110, separate from the BCM batch signatory release this companion documents).
Why it is invisible (the audit point): a raw UPDATE leaves no change document, no application-log entry, no authorization check at the write — so "who set/removed this block, and when?" has an empty audit trail; the block simply appears or disappears.
Scope: this acts on the document, not on who-signs — signatory selection is 100% standard (§3). Full task list, the other risks, and the fix → §9c (open issue #1) · source knowledge/domains/Treasury/code/YBSEG_REL.abap.
Two separate processes, in order:
① GROUPING (general BCM — §9a): a grouping process first assembles F110 payments into batches, by rule. It decides what is in a batch. No signatures here.
② APPROVE + SIGN workflow (§2 — this companion's focus): each batch is then released through a mandatory two-step control — Step 1: Approve / Validate, then Step 2: Sign / Commit — by two different people, in that order; both required, never simultaneous.
The two are independent. The only link is the RULE_ID that grouping stamps on the batch, which the validate step happens to read. Grouping = what is in the batch; the workflow = who releases it.
⚠ Banks are aligned OUTSIDE the system — SAP cannot enforce it
SAP's signatory node is entity-level — ONE panel for ALL of an entity's banks — but TRS registers a separate carton per bank. SAP can hold only one list and has no mechanism to detect two banks of the same entity drifting apart; that consistency is a manual / TRS control, not a system control. Detail + the compensating "alignment gate" → §5.

1 · Data model — three levels

LEVEL 1 · Entity
Company code (ZBUKR, e.g. UBO). This is the key that scopes the signatory nodes.
LEVEL 2 · Banks
House banks of the company code (T012/T012K). Each account has its own carton des signatures. The ones that reach BCM = those that produce batches.
LEVEL 3 · Signatory nodes
PD objects OTYPE='RY', key = entity × amount band. Bank-agnostic. Members in HRP1001.
Two different things are both called "rules" — don't confuse them:
• The batch-grouping rule (RULE_ID, e.g. UBO_AP_ST/MAX) decides how payments are bundled into a batch — it keys on grouping origin + paying company code + amount + payment method (real conditions in §9a). Not house bank.
• The release rules 90000005 (validate) and 90000004 (commit) are the two sequential approval STEPS (Step 1 → Step 2, see §2) — entity + amount tier only.
→ The bank is a criterion in neither layer — it is only carried on the batch (BNK_BATCH_HEADER.HBKID), never tested.

2 · Full flow (bank → people)

Every payment batch must pass two mandatory release steps before it reaches the bank — Step 1 Approve/Validate, then Step 2 Sign/Commit (detail in the callout below). The diagram shows how each step selects the people who act:

Node selection takes three inputs, and the bank is not one of them:

  1. Entity (ZBUKR=UBO) — hard-wired into every node's criteria → it picks which set of nodes applies (the "UBO" you see in each node name is this criterion, not a label).
  2. Rule / phase — 90000005 BNK_INI (validate) vs 90000004 BNK_COM (commit) → picks which step's nodes are evaluated.
  3. Amount — picks the tier within that entity+phase (≤10K vs higher).

So a payment lands on a node only when entity AND phase AND amount all match; the matching node's people (HRP1001) act. The bank only stamps the batch — it is never tested. Criteria detail (IT1218) → §3.

Two STEPS — approve THEN sign (never at the same time)

The "two rules" are not parallel rule types — they are the two sequential release steps of one approval procedure, run by the BCM release workflow WS50100024 → WS50100021 (standard BUSISB001). The same batch moves through them in order:

OrderRuleActionWhoNodes
Step 190000005 · BNK_INIApprove / Validate — check and release the batch for signingapproving officer"… Validation …" (50034892 / 50034893)
Step 290000004 · BNK_COMSign / Commit — sign and send the batch to the bankbank signatory"… signatures …" (50034894 / 50036737)

A batch must clear Step 1 before it reaches Step 2, and the two actions are performed by different people (segregation of duties / 4-eyes) — they never happen simultaneously. The entity + amount-tier selection runs independently at each step, which is why an unlimited signatory (e.g. Renata) is added to both the Validation and the Signature nodes — but acts at two different moments: first to validate, then to sign.

3 · Node selection — where the logic lives (IT1218)

How the rule picks ONE node: when a batch arrives, the rule scans every node's criteria and returns the node where all conditions match the batch. Those criteria are not the standard PFAC ones (HRP1222 is empty) — they live in infotype 1218 on each RY node (HRP1218 header → TABNR → HRT1218 expressions) and are matched against the standard BCM structure BNK_STR_BATCH_REL_APPR. (It IS standard BCM — the Approval Procedure generates them; it only looked non-standard because it bypasses the PFAC/1222 path.)

Read each row as: if batch.ZBUKR == UBO AND batch.amount ∈ [low,high] (and RULE_ID matches, on INI) → use this node.

THIS is where the node is selected — worked example (raw IT1218, live P01). The condition lives literally on each node. A UBO payment of USD 7,500 (batch ZBUKR=UBO, amount 7 500, RULE_ID=UBO_AP_MAX):

"Simulate rule resolution" — what it proves, and where its logic is defined
The simulation has no logic of its own. You give it a runtime container (Key date + Paying co. code + M.PymtAmt(rcur)) and it evaluates that against the criteria of each responsibility, then returns the matching node's agents. Worked example (rule 90000004 BNK_COM, key date 2026-06-19, co.code UBO, amount 100): → "Agent found" → AMARAL (10002437), BA (10005016), NOLETO JOVCHELOVITCH (10062474)… = members of node 50034894 (UBO ≤10K).

Where the logic is defined (your question): NOT in a program or exit — it is the criteria on each responsibility. In OOCU_RESP, double-click the responsibility (e.g. "UBO signatures up to 10.000") → its condition Paying co. code = UBO + M.PymtAmt 0–10000. That condition is infotype 1218 (HRP1218/HRT1218); the simulation just runs it. (PP01 doesn't surface it — the responsibility detail in OOCU_RESP does.)

Cross-check: the result includes BA (10005016) — agent determination returns him, but he has no BNK_APP role (§3e/§4b) so he still cannot sign. Determination ≠ authorization — that is exactly why the Access column (§4b) is mandatory alongside the node.

Custom logic lives in a SEPARATE gate — FI "Release for Payment" (WS90000003), not the BCM batch release
There are two distinct approval gates in the payment chain:
(1) FI Release for Payment — workflow WS90000003 (tasks "Determine subworkflow release for payt", "Release for payment single-stage" = std WS00400011, "Reset payment block"). A document/invoice-level gate, run before F110. This is where UNESCO's custom code is.
(2) BCM batch signatory release — workflow WS50100024 → WS50100021 (std BUSISB001), the topic of this companion, run after F110 on the payment file. Agent selection here is standard (RH_GET_ACTORS).

Gate (1) is where UNESCO's custom code sits — it sets the payment block via a direct DB write and reverses on reject; it acts on the document, not on who-signs. Full task list + the direct-UPDATE audit risk → §9c (open issue #1) and the callout at the top.

Plain reading: the grouping RULE_ID does double duty — it groups the batch and (via TBCA_RELPROC_EXP, step 3) selects the Dual-Control procedure. The procedure's step maps to a rule (90000004 commit / 90000005 validate); each rule owns a set of RY nodes (step 6); the node's IT1218 criteria (entity+amount) pick the one that matches; its HRP1001 people sign. "Configuring a node" = `OOCU_RESP` Change (people + IT1218). The determination FMs are standard; the only custom code is the reject BAdI.

3d · How to CHANGE it — plain-language guide (for a functional user)

Mental model: a node is just the list of people allowed to act for one entity + one amount range — SAP's version of the bank's signature card. There are two lists per payment (validate, then sign), and for some entities one list per amount tier. Every node is stamped with ZBUKR=<its entity> (proven above) — so changing people never touches the condition.

The everyday change — add / remove a signatory (≈95% of requests, e.g. INC-000011781):
  1. Transaction OOCU_RESP in Change mode (NOT "Simulate" — that only reads).
  2. Open the rule — BNK_INI (validate) or BNK_COM (sign) — then the node (e.g. UBO Validation up to 10.000 USD).
  3. Agent assignment → add the person (personnel number) or delimit (end-date) the one leaving, with valid-from / valid-to dates.
  4. Done — that person can now (or no longer) validate/sign for that entity + amount tier. You never edit the condition (ZBUKR / amount), only the people.
Who: DBS executes in P01 (we never write P01 — we hand them the spec).
The spec we hand DBS (unambiguous + safe) — one row per change:
Rule | Node (OBJID) | Node name | PERNR | Person | Action (ADD/DELIMIT) | valid-from/to
The OBJID is mandatory: node names look alike across entities (UBO/UIS/IIEP all have a "Validation" node) — using the number prevents editing the wrong panel. This is the §6 mandatory output.
Two things people forget
1. Being in the node is not enough to sign — the person also needs the SAP Security role BNK_APP (that was Renata's "not authorized" error). Separate ticket to Security.
2. Reconcile against the bank's carton des signatures — SAP is entity-level/bank-agnostic, so keeping the SAP panel = the bank's legal list is a manual control (the reconciliation in §5), not something SAP enforces.
Rare changes (config / BASIS — not day-to-day): change a node's amount band ("up to X") or add a new tier / entity → done in the Approval Procedure customizing, which regenerates the node's IT1218 condition. Not a signatory-list change.

5 · Reconciliation & gates

Target = the single agreed panel, split by tier (≤10K-only vs unlimited). Current = live HRP1001 membership (all periods) of the entity's RY nodes. Classify every (node × person):

ConditionVerdict
On carton & active in SAPkeep
On carton & absent/expired in SAPADD  (current ask if in the letter; otherwise TRS gap)
"Delete" in the letter & active in SAPDELIMIT  (current ask)
Active in SAP & on no cartonover-authorization → DELIMIT  (TRS, old issue)
Completeness gate. Require a current carton for every BCM bank of the entity — the banks that actually produce batches (BNK_BATCH_HEADER; a subset of T042A). If any is missing → do NOT flag "SAP-extra" as drift; emit INCOMPLETE: missing cartons for <HBKID…>.
Alignment gate. All those cartons must be identical. If they diverge → HALT and escalate to TRS — the single entity-level node cannot represent two different panels.
⚠ Why the alignment gate exists: the bank panels are not controlled by SAP
TRS issues a separate letter/carton to each bank, and each bank registers it on its own. SAP holds one panel per entity (all its banks share it), so it physically cannot give Citibank a different signatory list than Banco do Brasil. Nothing in the system detects or prevents two banks of the same entity/country from diverging — that consistency is enforced outside SAP (TRS process / manual). This gate is the only place the routine catches a divergence.
Tier mapping (validated by Amaral): "up to 10,000 only" → ≤10K nodes only; "unlimited" → all tier nodes of both rules.

6 · MANDATORY output structure

ONE table of the node's ACTIVE members only (one row each) plus the additions. Expired/red OOCU_RESP rows are not in the table; if an expired row carries an action (re-add, or the person is still active on another node) it goes in the net-operations Old issues. Columns: Rule | Node (OBJID) | Node name | PERNR | Person | Live status | Carton | Access (BNK_APP role) | Action. The Access column (the §3e check) flags whether the person's SAP user holds a BNK_APP-granting role — every ADD with ❌ needs a paired Security/PFCG ticket, not just the node change. Legend: ✅ keep ➕ ADD (current ask) ➖ DELIMIT (current ask) ⚠️ TRS (old issue) — no action. Then a net-operations summary split into Current ask (authorized by the letter) vs Old issues (need TRS sign-off).

1 · Direct DB write instead of a BAPI (the main one). YBSEG.ZCREATEPAYMENTBLOCKWF sets the payment block with raw UPDATE bseg / UPDATE bsik SET zlspr='W' — not FI_DOCUMENT_CHANGE / BAPI_ACC_* nor the standard Release-for-Payment block. Consequences: no change documents (no audit trail of the block), no validation/substitution/authority check, no enqueue (lock), and BSEG and BSIK updated separately → if one fails the document is inconsistent. Plus COMMIT WORK inside a BOR method (workflow LUW). Recommend: replace with the standard payment-release block or a supported change API.

13 · Anti-patterns & safeguards

RiskSafeguard
Lookalike nodes: several end in "Validation" and sit adjacent (IIEP 50010087, UIS 50036801, UBO 50034892…). Near-miss INC-000006313 P2: Svein added to IIEP by mistake.ALWAYS identify by RY OBJID, never by name. The mandatory table carries OBJID on every row.
Ghost PERNR: a row points to a PERNR with PA0002 but no PA0105/0001 (no SAP user) → the workflow can't route to it → signatory silently disabled.Validate the user in PA0105/USR02 (phase 3). The HEPATUS carton is the authoritative PERNR source.
Screenshots mislead: OOCU_RESP with "Other period" shows/hides expired rows (red X); a person can have an expired + an active row (Martin in 50034893).Read HRP1001 all periods, live; never conclude from an image.
Banks not aligned (see ⚠ top): two banks of the same entity with different cartons.The alignment gate (§5) — SAP can't catch it, so the routine must. Escalate to TRS.
Stale Gold-DB snapshot.Refresh extract_bcm_signatories.py before trusting counts.
Writing to P01.Forbidden for the agent. Read-only; DBS executes.
