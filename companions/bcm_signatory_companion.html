BCM Bank Signatory — Companion

How payment signing/approval works in SAP Bank Communication Management (UNESCO) and how to resolve a signatory-panel change. All data is read live from P01 via RFC — not from screenshots. P01 is read-only for the agent; DBS executes changes in OOCU_RESP. · v2 · 2026-06-18 · origin: INC-000011781.

Two separate processes, in order:
① GROUPING (general BCM — §9a): a grouping process first assembles F110 payments into batches, by rule. It decides what is in a batch. No signatures here.
② APPROVE + SIGN workflow (§2 — this companion's focus): each batch is then released through a mandatory two-step control — Step 1: Approve / Validate, then Step 2: Sign / Commit — by two different people, in that order; both required, never simultaneous.
The two are independent. The only link is the RULE_ID that grouping stamps on the batch, which the validate step happens to read. Grouping = what is in the batch; the workflow = who releases it.
⚠ Banks are aligned OUTSIDE the system — SAP cannot enforce it
Each bank registers its signatory panel independently: TRS sends a separate letter + carton to each bank. But SAP's signatory node is entity-level — ONE panel for ALL of an entity's banks — so it can hold only one list and has no mechanism to detect or prevent two banks of the same entity (same country) from drifting apart. If bank A's carton ≠ bank B's carton, the single node is wrong for at least one bank and nothing in SAP flags it. Keeping the panels aligned is a manual / TRS governance control, not a system control. The "alignment gate" in §5 is the compensating check this routine adds.

1 · Data model — three levels

LEVEL 1 · Entity
Company code (ZBUKR, e.g. UBO). This is the key that scopes the signatory nodes.
LEVEL 2 · Banks
House banks of the company code (T012/T012K). Each account has its own carton des signatures. The ones that reach BCM = those that produce batches.
LEVEL 3 · Signatory nodes
PD objects OTYPE='RY', key = entity × amount band. Bank-agnostic. Members in HRP1001.
Two different things are both called "rules" — don't confuse them:
• The batch-grouping rule (RULE_ID, e.g. UBO_AP_ST/MAX) decides how payments are bundled into a batch — it keys on grouping origin + paying company code + amount + payment method (real conditions in §9a). Not house bank.
• The release rules 90000005 (validate) and 90000004 (commit) are the two sequential approval STEPS (Step 1 → Step 2, see §2) — entity + amount tier only.
→ The bank is a criterion in neither layer — it is only carried on the batch (BNK_BATCH_HEADER.HBKID), never tested.

2 · Full flow (bank → people)

Every payment batch must pass two mandatory release steps before it reaches the bank — Step 1 Approve/Validate, then Step 2 Sign/Commit (detail in the callout below). The diagram shows how each step selects the people who act:

Node selection takes three inputs, and the bank is not one of them:

  1. Entity (ZBUKR=UBO) — hard-wired into every node's criteria → it picks which set of nodes applies (the "UBO" you see in each node name is this criterion, not a label).
  2. Rule / phase — 90000005 BNK_INI (validate) vs 90000004 BNK_COM (commit) → picks which step's nodes are evaluated.
  3. Amount — picks the tier within that entity+phase (≤10K vs higher).

So a payment lands on a node only when entity AND phase AND amount all match; the matching node's people (HRP1001) act. The bank only stamps the batch — it is never tested. Criteria detail (IT1218) → §3.

Two STEPS — approve THEN sign (never at the same time)

The "two rules" are not parallel rule types — they are the two sequential release steps of one approval procedure, run by workflow 90000003. The same batch moves through them in order:

OrderRuleActionWhoNodes
Step 190000005 · BNK_INIApprove / Validate — check and release the batch for signingapproving officer"… Validation …" (50034892 / 50034893)
Step 290000004 · BNK_COMSign / Commit — sign and send the batch to the bankbank signatory"… signatures …" (50034894 / 50036737)

A batch must clear Step 1 before it reaches Step 2, and the two actions are performed by different people (segregation of duties / 4-eyes) — they never happen simultaneously. The entity + amount-tier selection runs independently at each step, which is why an unlimited signatory (e.g. Renata) is added to both the Validation and the Signature nodes — but acts at two different moments: first to validate, then to sign.

3 · Node selection — where the logic lives (IT1218)

How the rule picks ONE node: when a batch arrives, the rule scans every node's criteria and returns the node where all conditions match the batch. Those criteria are not the standard PFAC ones (HRP1222 is empty) — they live in infotype 1218 on each RY node (HRP1218 header → TABNR → HRT1218 expressions) and are matched against the standard BCM structure BNK_STR_BATCH_REL_APPR. (It IS standard BCM — the Approval Procedure generates them; it only looked non-standard because it bypasses the PFAC/1222 path.)

Read each row as: if batch.ZBUKR == UBO AND batch.amount ∈ [low,high] (and RULE_ID matches, on INI) → use this node.

⚠ Notice what is MISSING: there is no bank (HBKID) column
The selection key is entity (ZBUKR) + amount only — the node literally cannot tell one bank from another. This is the technical root of the warning at the top: because selection ignores the bank, one node serves ALL of the entity's banks, so SAP has no way to give Citibank a different signatory list than Banco do Brasil — and no way to detect if their cartons disagree. Bank-to-bank alignment is therefore a control outside the system (TRS / manual), not something SAP enforces.
On RULE_ID (avoid confusion): it is the batch-grouping rule, not an amount label — don't read "MAX"/"ST" as a size. The actual tier driver is MAXPAYAMT_RULECURR; the RULE_ID pairing is just how UBO's approval procedure happens to be configured.

5 · Reconciliation & gates

Target = the single agreed panel, split by tier (≤10K-only vs unlimited). Current = live HRP1001 membership (all periods) of the entity's RY nodes. Classify every (node × person):

ConditionVerdict
On carton & active in SAPkeep
On carton & absent/expired in SAPADD  (current ask if in the letter; otherwise TRS gap)
"Delete" in the letter & active in SAPDELIMIT  (current ask)
Active in SAP & on no cartonover-authorization → DELIMIT  (TRS, old issue)
Completeness gate. Require a current carton for every BCM bank of the entity — the banks that actually produce batches (BNK_BATCH_HEADER; a subset of T042A). If any is missing → do NOT flag "SAP-extra" as drift; emit INCOMPLETE: missing cartons for <HBKID…>.
Alignment gate. All those cartons must be identical. If they diverge → HALT and escalate to TRS — the single entity-level node cannot represent two different panels.
⚠ Why the alignment gate exists: the bank panels are not controlled by SAP
TRS issues a separate letter/carton to each bank, and each bank registers it on its own. SAP holds one panel per entity (all its banks share it), so it physically cannot give Citibank a different signatory list than Banco do Brasil. Nothing in the system detects or prevents two banks of the same entity/country from diverging — that consistency is enforced outside SAP (TRS process / manual). This gate is the only place the routine catches a divergence.
Tier mapping (validated by Amaral): "up to 10,000 only" → ≤10K nodes only; "unlimited" → all tier nodes of both rules.
