Reversal Applies to BOTH Open Items and Balances — Two Valuation Modes

Common misconception: "reversal only applies to Open Items" Not true. SAP F.05 reverses both open-item and G/L-balance valuations. The difference at UNESCO is a matter of which valuation mode each run uses — and both modes are legitimate accounting practice. The mode determines whether a reversal is created.

Mode A — Reversing Valuation (interim/monthly)

How it works: Post unrealized FX gain/loss at month-end → reverse it on day 1 of the next month. The valuation is a temporary snapshot.

Why reverse: The figure is provisional. When the underlying item (open item, or bank balance) actually moves, the real realized gain/loss is what counts. Reversing avoids double-counting.

Applies to: Both Open Items and G/L Balances. Controlled by the "Reversal posting date" + reverse flag in the variant.

UNESCO Open Items: all run in this mode — valuation + reversal confirmed in BKPF for all 8 OI institutes.

Mode B — Balance Sheet Preparation Valuation (permanent)

How it works: Post the valuation permanently — it is written to the account's valuation-difference field and is not reversed. The next run calculates the delta from this stored value.

Why no reverse: Used to establish the official balance-sheet position (typically year-end). The valuation becomes the carried position, so reversing it would be wrong.

Applies to: G/L Balances, via the Bal.sheet preparation valuatn checkbox on the Postings tab.

UNESCO Balances: run in this mode — valuation posts monthly, no reversal. This is the expected, standard treatment for bank/cash balances: the account carries its revalued position and the next run posts only the delta. Not a defect.

This is normal — bank-balance valuation is not meant to reverse The absence of day-1 reversals on the _UNBA (balance) runs is the correct behaviour, not a missing step. Bank and cash balances are revalued to the period-end rate and the valuation is carried forward (Mode B above); the following month posts only the change. This is why all 8 institutes with balance variants show valuation-without-reversal — they are consistent with each other and with standard practice.

Note on UIL: UIL has a single balance reversal (Jan 2025). That one-off is the deviation from the norm — likely a manual interim adjustment — not evidence that the others are wrong. To document the configured mode definitively, open a _UNBA variant in F.05 and read the Bal.sheet preparation valuatn setting (not extractable via RFC — VARI/VARIS are pool tables returning only the variant name).

🏛️ Closing Activities — Domain Overview

Closing Activities tracks all period-end and year-end accounting activities — what runs, who runs it, when, whether it ran correctly, and whether anyone can prove it ran. Each activity is a recurring step that must complete before a fiscal period can be locked. Today most run interactively, with no scheduling and no execution visibility; a period can close with or without FX revaluation and no one is alerted.

The opportunity — not the error The headline is not a bug. It is that these recurring close tasks can be automated and instrumented for visibility — turning "we think it ran" into "the job log proves it ran, on time, completely." FX revaluation is the first worked example: scheduling SM36 jobs (the infrastructure already exists — SAPF124 runs this way daily) would remove missed months, timing lag, single-point-of-failure and the absence of a sign-off gate, all at once.
How we know this — process mining We reconstructed the entire reality of this process — who runs it, when, the gaps, the configuration and the root cause — purely by mining logs, data, tables and code (BKPF/BSIS, GLT0, T030H, VARI/VARIS, OB09/FS00), without interviews or guesswork. Read the system, not the documentation. This is the reusable lens for every domain: understand how it works → identify what to improve → automate and give execution visibility → resolve each incident with full context. (Aligns with the project North Star — SAP Agentic AGI.)
The error along the way — minor, immediate One small configuration item surfaced: an unfinished Banco de Chile sub-account migration in OB09 (2 accounts post their FX adjustment to a closed sub). Fix = 2 OB09 entries. Plus four operational findings (ICTP coverage gap, single-user fragility, MGIE reversal inconsistency, UBO variant mislabeling); several earlier "alarms" (balance non-reversal, 102 "empty" accounts) were reviewed and cleared as benign. Detail in the Forensic and T030H sections.

📊 FX Revaluation (F.05 / SAPF100) — 2025 Production Analysis

All FX revaluation at UNESCO is executed interactively with no background job. Accountants launch F.05 / SAPF100 manually from their session — the program calculates amounts and posts documents with TCODE=FBB1 in BKPF. FBB1 is the program's internal posting transaction, not manual line-by-line data entry. The program is fully configured (T044A, T030H, OBA1) but has zero scheduled SM36 background jobs.

The standard cycle confirmed from 11,793 production documents:

🚩 Flags & Critical Issues (from 2025 Production)

These are the findings that survived verification. Each is anchored in production data (BKPF/BSIS/T030H/SKB1/GLT0). The single genuine configuration error is the blocked FX-difference accounts in OBA1 (4 of them; see Forensic + T030H sections); the rest are operational/process flags. Note: balance valuations not reversing and the 102 "empty" T030H rows were reviewed and are not flagged — they are normal (see Forensic section).

🔴 ICTP — 2 Missed Months (July + November 2025)

  • M_VENUTI posted day-1 reversals for both months (10 reversal docs each)
  • Zero corresponding month-end valuation documents found
  • Consequence: 2 months of FX exposure unrecognized — reversed against nothing
  • Root cause: M_VENUTI absent, no backup user for ICTP
  • Will recur in 2026 without backup assignment

Fix: Assign backup user + create SM36 job so absence doesn't matter

🔴 UBO — Chronic Late Posting (avg 24.3 days)

  • P_TUCKER routinely posts revaluation 3–4 weeks after month-end
  • Worst case observed: 62 days late (over 2 months)
  • No backup user identified for UBO
  • UBO financial statements reflect FX exposure with significant delay
  • Despite lateness, all 12 months were eventually posted (process awareness exists)

Fix: SM36 job eliminates lag entirely

🔴 UNES — Reversal Systematically Late (avg 11.8 days)

  • J_LA's reversals average 11.8 days into the new month
  • Maximum observed: 40 days after the reversal BUDAT
  • For UNES (largest co-code, 1,014 T030H rows), this is highest-impact
  • Prior month's unrealized FX sits in books ~2 weeks into new period
  • Creates overlap between prior-month valuation and current-month exposure

Fix: SM36 reversal job on day 1 at 06:00 eliminates this entirely

🟡 MGIE — Mid-Month Posting Pattern (not standard month-end)

  • P_ARORA shows negative CPUDT lag values — FX entries posted mid-month, before month-end
  • This does not match the standard last-day valuation / day-1 reversal pattern
  • K_BHATIA (avg 14d lag) handles some months
  • MGIE is smallest co-code by FX volume (3 blocked accounts in SKB1)
  • Risk is lower but process is unclear and needs documentation

Action: Interview P_ARORA — understand if this is intentional or a process gap

🟡 No Formal Close Gate — Period Locks Without FX Sign-Off

  • SAP period lock (OB52 / MMPV) runs independently of FX revaluation status
  • A period can close with revaluation completely missing — no alert, no block, no notification
  • This is exactly how ICTP's July and November 2025 gaps occurred silently
  • The ICTP case was only discovered retroactively via BKPF data mining — it was not caught at close time
  • Finance management had no visibility that 2 months of ICTP FX exposure were unrecognized until this analysis

Fix: Add FX sign-off prerequisite to the period close checklist. For automation: the SM36 job log itself becomes the sign-off evidence.

The genuine defect is small: 4 FX-difference (adjustment) accounts configured here are blocked for posting, referenced by 6 active bank accounts (the error fires only when one carries an FX balance). How It Happens

F.05 reads T030H for each account being revalued and looks up its balance-sheet adjustment account (LKORR). For the Banco de Chile mains, that adjustment account is the closed sub-account (1109574 / 1109571) instead of the active sub (1110574 / 1110571) — so F.05 cannot post and aborts with "Account 1109574 is blocked for posting." This is the unfinished sub-account migration explained in the Forensic section above: the old sub was retired, but OB09 was never repointed to the new active sub.

Fix = repoint OB09 to the active sub (see Forensic → "Fix" for the full detail). Do NOT unblock the closed subs (retired on purpose). Repoint 1010574 → 1110574 and 1010571 → 1110571 (the 2 in-scope accounts), matching the Ecobank pattern. Confirm with Treasury that 1110574/1110571 is the migration target.

Is it excluded in the variant? No — the error proves it

We could not read the variant's exclusion entries directly (VARIS is a pool table; RFC returns only the variant name — needs the F.05 screen or D01 + S_DEVELOP). But the logic is conclusive: an excluded account never reaches account determination, so it cannot produce "blocked for posting." The error occurring at runtime proves the account is in scope, not excluded. To list any exclusions for other accounts, open F.05 → UNES_UNBA → selection options and look for sign='E' entries.

Why the Other Blocked-Adjustment Cases Don't Error

284 distinct HKONTs have a blocked adjustment account (289 T030H rows). Of those, 278 are themselves blocked (XSPEB='X') — F.05 skips blocked source accounts entirely, never reaching the determination, so no error. Only 6 active accounts reference a blocked adjustment account, and of those the error fires only when the account carries an FX balance to revalue (currently the CLP/USD/XOF accounts with a balance). The other 278 are excluded from scope silently and correctly (closed accounts that should not be revalued anyway).
