The ask is exactly right and the mechanism exists. There is a list, it is maintained, and adding a country to it is configuration — no development. What follows is what to enter and what still has to be decided.

2 · What Citi asked for — and the one sentence that fixes the design

"Purpose of Payment (PoP) information is an existing regulatory requirement for payments destined for or originating within Egypt. Effective September 5th, 2026, payment instructions submitted through its channels for all Real Time Gross Settlement (RTGS) and Cross Border Funds Transfers (CBFT) which do not include Purpose of Payment will not be processed."
"…accurately populate the Purpose of Payment information in the Transaction Details / Payment Details field, or SWIFT Field 70, when initiating any relevant payment through our channels."
"the PoP should clearly and concisely describe the reason for the payment. Examples: Payment for goods received under Invoice 12345 · Service fees for consulting work · Salary payment · Investment · Loan repayment"
SWIFT :70 is Remittance Information, and in ISO 20022 that is RmtInf/Ustrd — nothing else. So Egypt's YTFI_PPC_TAG row is USTRD, the family BH/ID/IN/JO/MA/MY/PH already use. It is not INSTRINF, which renders InstrForCdtrAgt = SWIFT :72, a different field, used by AE and CN. One sentence in the notice removes the only structural choice there was.
And there is no code list in the request. Egypt is not an AE/JO-style country where the bank dictates numeric codes — it asks for a description. So the load-bearing block is PPC_DESCR (the narrative), not PPC_VAR. Citi's own first example ties the description to the invoice, which is what PAY_FIELD FPAYP-XBLNR already emits.
Scope: RTGS and CBFT, for payments "destined for or originating within Egypt" — so both the local EGP01 account and the cross-border USD01 one. Configuration is per country, which is exactly how YTFI_PPC_STRUC.LAND1 is keyed.

4 · The reason list — derived, then verified claims 490 · 495

Are the lists international? Measured: no — 7 of 9 are national and none overlaps. India uses RBI codes, Indonesia Bank Indonesia numerics, Jordan the Central Bank of Jordan list, Morocco the Office des Changes, Malaysia Bank Negara, China slash-notation. The only shared set is AE ∩ BH — six CBUAE mnemonics Bahrain reused.

One country already solves the "no national list" case: the Philippines uses ISO 20022 ExternalPurpose codes — SUPP · SALA · BEXP · CHAR. That is the in-house precedent for Egypt, where Citi named no code list at all.

With one caveat found in the research: the Philippines list also contains PH3 = TRVL, and TRVL is not an ISO 20022 code. So the existing configuration is not uniformly standards-based — calling the Philippines "the ISO precedent" overstates it.

5 · Why this will work, and exactly how far claim 494

6 · The one limit that survives every correction

The configuration protects company code UNES and nobody else. U917 is step 012 of validation UNES, which OB28 assigns to UNES alone. ICTP runs 4 steps, IIEP 2, UBO 3, UIL 1, UIS its own; IBE, ICBA and MGIE have no validation at all. claim 485

Of the 17,778 lines to Egypt-domiciled payees, 1,720 sit in institutes with no capture control — ICTP 1,242 · UIL 348 · IIEP 117 · UIS 9 · UBO 4. Whether they get an equivalent step is a functional decision: KU-2026-099-PPC-INSTITUTE-COVERAGE.
And one process question the configuration cannot answer. A small slice of Egypt payments leaves as a pre-numbered cheque with no SAP file at all — 3% of lines, 6% of value in 2026 (§6). For those, the instruction is issued outside SAP and somebody has to populate the Purpose of Payment in the bank's own portal. 7 · Corrected scope — the population is ~10x larger than first reported claim 489

I read REGUH-UBNKS as the beneficiary's bank country. It is OUR house bank's country. Each HBKID maps to exactly one UBNKS across the whole table — SOG01 → FR across 1,943,748 lines as a single distinct value, CIT19 → EG, CIT04 → US. A payee-bank field cannot behave that way. UBNKS/UBNKL/UBKNT/UBHKT are the house-bank block. The beneficiary's bank country is LFBK-BANKS — which is exactly what U917 reads.

9 · Does the super-user exception apply here?

No. U917 cannot be bypassed per user. Verified against the source: its body (YRGGBS00:1547-1590) contains zero occurrences of yxuser and zero of xtype. Of the eight routines in this form pool that can block a posting, only U913 carries the bypass.

11 · The configuration, step by step

Read this before deciding the transport plan. The switch is YTFI_PPC_STRUC — not T015L. The moment those rows exist in P01, every FB60 / MIRO / FB01 posting in company code UNES to a vendor whose LFBK-BANKS = EG is blocked unless the purpose code is filled. T015L and YTFI_PPC_TAG are inert on their own.

So this goes in two transports. Put them in one and the block starts the second the import finishes — with no warning to Cairo and no training done. All nine configured countries block today; Egypt will be the tenth.

state as of 2026-08-19 It is currently ONE transport, and that still has to be split. D01K9B0FXE (parent) / D01K9B0FXF (task), unreleased, 17 keys: T015L 5 + YTFI_PPC_STRUC 11 + YTFI_PPC_TAG 1.

And a near miss worth keeping. The eleventh YTFI_PPC_STRUC key is not Egypt's — it is 350ID USTRD O01, Indonesia's first separator, which had been blanked in D01 while Egypt was being maintained. Had the transport been released in that state it would have shipped Indonesia from /PURP/<code>/<XBLNR> to PURP/<code>/<XBLNR> for Bank Indonesia, across 921 lines that carry a purpose code. The value was restored the same day and verified byte-identical to P01, so the key is now a no-op — a table transport stores the key and exports the value at release time. The key should still be removed so the transport says only what it changes.

The generalisable part: maintaining one country in SM30 can capture a neighbouring country's key into the transport, and the diff that catches it is the one over the whole table, D01 against P01 — never the diff of the keys you meant to touch. claim 526

The separator trap, and why it is not obvious. The first build left every SEPARATOR empty, on the reasoning that "the structure is simple text, no separations needed". It is not: YCL_IDFI_CGI_DMEE_UTIL->BUILD_VALUE is literally ev_value_c = |{ iv_value_c }{ iv_value_to_add }| — direct concatenation, no implicit separator of any kind. The file would have read Payment for goods or services receivedINV5105551234, all glued.

And a separator of one space does not work either. PPC_VALUE is CHAR(60), so a trailing space is indistinguishable from the field's own padding — there is no way to store it. A leading space does survive: " INV" was saved through SM30 and read back over RFC with one leading blank intact. So separation can be put in front of any literal and never behind one — and therefore never immediately before a PAY_FIELD, which is a dynamic field and takes no prefix.
