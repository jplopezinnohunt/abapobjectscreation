Hence I kindly request you to include this with the list of the countries which need this information. This requirement is going to be mandatory effective September 5th 2026." — Mathewos Mehari, 10 Aug 2026
"From my understanding, we need to add Egypt on the list of the mandatory purpose code countries, before September 5th, 2026." — Christina Lopez-Chemouny
The ask is exactly right and the mechanism exists. There is a list, it is maintained, and adding a country to it is configuration — no development. What follows is what to enter and what still has to be decided.

2 · What Citi asked for — and the one sentence that fixes the design

"Purpose of Payment (PoP) information is an existing regulatory requirement for payments destined for or originating within Egypt. Effective September 5th, 2026, payment instructions submitted through its channels for all Real Time Gross Settlement (RTGS) and Cross Border Funds Transfers (CBFT) which do not include Purpose of Payment will not be processed."
"…accurately populate the Purpose of Payment information in the Transaction Details / Payment Details field, or SWIFT Field 70, when initiating any relevant payment through our channels."
"the PoP should clearly and concisely describe the reason for the payment. Examples: Payment for goods received under Invoice 12345 · Service fees for consulting work · Salary payment · Investment · Loan repayment"
SWIFT :70 is Remittance Information, and in ISO 20022 that is RmtInf/Ustrd — nothing else. So Egypt's YTFI_PPC_TAG row is USTRD, the family BH/ID/IN/JO/MA/MY/PH already use. It is not INSTRINF, which renders InstrForCdtrAgt = SWIFT :72, a different field, used by AE and CN. One sentence in the notice removes the only structural choice there was.
And there is no code list in the request. Egypt is not an AE/JO-style country where the bank dictates numeric codes — it asks for a description. So the load-bearing block is PPC_DESCR (the narrative), not PPC_VAR. Citi's own first example ties the description to the invoice, which is what PAY_FIELD FPAYP-XBLNR already emits.
Scope: RTGS and CBFT, for payments "destined for or originating within Egypt" — so both the local EGP01 account and the cross-border USD01 one. Configuration is per country, which is exactly how YTFI_PPC_STRUC.LAND1 is keyed.

4 · The reason list — derived, then verified claims 490 · 495

Are the lists international? Measured: no — 7 of 9 are national and none overlaps. India uses RBI codes, Indonesia Bank Indonesia numerics, Jordan the Central Bank of Jordan list, Morocco the Office des Changes, Malaysia Bank Negara, China slash-notation. The only shared set is AE ∩ BH — six CBUAE mnemonics Bahrain reused.

One country already solves the "no national list" case: the Philippines uses ISO 20022 ExternalPurpose codes — SUPP · SALA · BEXP · CHAR. That is the in-house precedent for Egypt, where Citi named no code list at all.

With one caveat found in the research: the Philippines list also contains PH3 = TRVL, and TRVL is not an ISO 20022 code. So the existing configuration is not uniformly standards-based — calling the Philippines "the ISO precedent" overstates it.

5 · Why this will work, and exactly how far claim 494

No ABAP is needed — and that is now mechanical, not an assumption. The BAdI is selected by the country of our paying house bank (FPAYHX-UBISO), which for SocGen is FR; the class then looks up the config by the country of their bank (FPAYH-ZBNKS). All three layers are generic — u917 reads LFBK-BANKS, CM002 passes ZBNKS, CM003 filters WHERE LAND1 = IV_LAND1, with no country literal in any of them. Nine beneficiary countries already resolve through the same single class. See the mechanism companion, §3b.

Which country to copy — and why not the obvious one

Copying a country means copying its shape, never its values: the FIXED_VAL entries are local central-bank codes and the T015L list is country-specific. The shapes differ on six axes:

AxisVariation across the nine
Tag familyINSTRINF (AE, CN) vs USTRD (the other seven)

PAY_FIELDAE, BH, CN use none; the other six append FPAYP-XBLNR (O) and FPAYP-SGTXT (P/R)

India is the template. Citi asks for a description and ties it to the invoice. India is the only configured country that emits code + description + invoice reference. Bahrain emits a description but no invoice; the other seven emit no description at all.
One thing not to copy: the missing R. BH, MY and PH have no Payment request rows, so a Treasury payment request to those countries emits nothing — silently. Egypt must define all three pay types.

The one thing still unproven

Whether the Ustrd node in the /CGI_XML_CT_UNESCO tree carries the exit call. DMEE_TREE_NODE rejects an RFC_READ_TABLE WHERE clause on this system (string columns), so it could not be read directly. Close it with a D01 test: one vendor with an Egyptian bank, one F110 run, read the XML. That is the acceptance test for this change anyway.

6 · The one limit that survives every correction

The configuration protects company code UNES and nobody else. U917 is step 012 of validation UNES, which OB28 assigns to UNES alone. ICTP runs 4 steps, IIEP 2, UBO 3, UIL 1, UIS its own; IBE, ICBA and MGIE have no validation at all. claim 485

Of the 17,778 lines to Egypt-domiciled payees, 1,720 sit in institutes with no capture control — ICTP 1,242 · UIL 348 · IIEP 117 · UIS 9 · UBO 4. Whether they get an equivalent step is a functional decision: KU-2026-099-INSTITUTE-COVERAGE.
And one process question the configuration cannot answer. A small slice of Egypt payments leaves as a pre-numbered cheque with no SAP file at all — 3% of lines, 6% of value in 2026 (§6). For those, the instruction is issued outside SAP and somebody has to populate the Purpose of Payment in the bank's own portal. KU-2026-099-EGYPT-INSTRUCTION-CHANNEL — Treasury (Ingrid Wettie / Mathewos Mehari) + the Cairo office, before 5 September.

7 · Corrected scope — the population is ~10x larger than first reported claim 489

I read REGUH-UBNKS as the beneficiary's bank country. It is OUR house bank's country. Each HBKID maps to exactly one UBNKS across the whole table — SOG01 → FR across 1,943,748 lines as a single distinct value, CIT19 → EG, CIT04 → US. A payee-bank field cannot behave that way. UBNKS/UBNKL/UBKNT/UBHKT are the house-bank block. The beneficiary's bank country is LFBK-BANKS — which is exactly what U917 reads.

Citi binds payments "destined for or originating within" Egypt. That is two populations, and they behave very differently:

PopulationHow to find itLinesU917 would block
Originating in Egypt — paid from our Citibank Egypt accountHBKID='CIT19'39265 (17%)
Destined for Egypt — the beneficiary banks in Egypt, method NLFBK-BANKS='EG'9,0958,103 (89%) · ~USD 41.5M
The request is worth far more than first assessed. The control is well designed for the destined-for half — 89% coverage, and those payments do produce a payment file, so both capture and rendering apply. It is weak only on the originating-in half: 254 of those 392 lines go to payees with no LFBK row at all, so CHECK lv_banks IS NOT INITIAL exits and the control never fires. Those are the cheques.
A master-data ceiling no configuration can lift. 1,225 of 2,762 Egypt-domiciled vendors (44%) have no LFBK row. For every one of them U917 is inert whatever you put in YTFI_PPC_STRUC. If those vendors are ever paid by transfer, they must get bank master data first — and that is a separate piece of work.

The cheque hole is small, and this reverses an earlier conclusion of mine. I had read the historic CIT19 population (392 lines all-time) as the Egypt case and concluded the rendering half was moot because "it is all cheques". In 2026 that account issued 8 lines. The real Egypt volume is transfers to Egyptian-banked vendors — 97% of lines and 94% of value are reachable by the control, and those payments do produce a payment file, so capture and rendering both apply.

9 · Does the super-user exception apply here?

No. U917 cannot be bypassed per user. Verified against the source: its body (YRGGBS00:1547-1590) contains zero occurrences of yxuser and zero of xtype. Of the eight routines in this form pool that can block a posting, only U913 carries the bypass.
Blocking routine in YRGGBS00Reads YXUSER?
U917 — purpose of paymentno — cannot be bypassed
U913 — special budget codesYES (line 971)
U901 · UM906 · UM907 · UXR2 · U915 · U916no

The other three YXUSER readers — UAEP (1129), UATF (1315), NSAI (1421) — are substitutions on asset postings, not validations.

But three other exception routes do exist, and they matter more than the user table.
RouteEffect on the Egypt controlStatus
Company code has no UNES validation assigned (OB28)The control never runs. This is the real exception, and it applies to 8 of 9 institutesmeasured — claim 485
The validation is deactivated at OB28 activation levelturns it off for everyone in that company codenot currently the case for UNES

The honest summary for an auditor: no individual can be granted an exemption from the purpose-of-payment block. The exposure is not per person — it is per company code, and per channel.

11 · The configuration, step by step

Read this before deciding the transport plan. The switch is YTFI_PPC_STRUC — not T015L. The moment those rows exist in P01, every FB60 / MIRO / FB01 posting in company code UNES to a vendor whose LFBK-BANKS = EG is blocked unless the purpose code is filled. T015L and YTFI_PPC_TAG are inert on their own.

So this goes in two transports. Put them in one and the block starts the second the import finishes — with no warning to Cairo and no training done. All nine configured countries block today; Egypt will be the tenth.

Transport 1 — inert. Can go any time.

Step 1 · T015L — the code list. SM30 → view V_T015L ("SCB indicators"). Ten new rows. BLART and LVAWV are constant across all 73 existing rows — match them exactly. Leave ZWCK2 and EDIBL empty (only 1 of 73 rows uses ZWCK2).

Nothing stops a user picking JO6 on an Egyptian payment, and the validation will accept it because it only checks the field is not empty. See improvement #1 in the solution companion.

Step 4 · the block. In D01, take a vendor with LFBK-BANKS = EG. Post FB60 leaving the purpose code empty → must fail on validation UNES step 012, CHECKID 2UNES###009. Fill EG0 → posts.
