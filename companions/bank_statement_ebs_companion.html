🔑 Step 0 of the chain — how SAP decides WHICH account a file belongs to (added s108, INC-000013624)

The seven steps below all assume the statement has already been matched to a house bank account. That matching is a separate two-hop lookup, and it is where a change of account number silently kills the channel.

The Complete E2E Bank Statement → Posting Chain

Every bank transaction follows these 7 steps. Each step is a configuration lookup that transforms the raw bank data into an SAP posting.

STEP 1: BANK SENDS MT940 FILE Bank (Societe Generale, Citibank, SCB, etc.) → SWIFT Alliance Lite2 (3-min poll HQ / 15-min field offices) → File lands in \\hq-sapitf\SWIFTS\output\ → FF_5 background job picks it up (91.2% automated by JOBBATCH) STEP 2: IDENTIFY BANK FORMAT (T028B) The bank's physical account number (BANKL + KTONR) → Maps to VGTYP (transaction type format) → Maps to BNKKO (house bank + account ID) Example: Bank number "FR7630003" + Account "01752024A" → VGTYP = SOG_FR (Societe Generale France format) → BNKKO = SOG01-EUR01 STEP 3: PARSE EXTERNAL TRANSACTION CODE (MT940 Tag 61) MT940 Tag 61 contains the bank's transaction code: :61:2403271327D1234,56NTRF//REF123 NTRF = Transfer This becomes VGEXT (external transaction code) in FEBEP STEP 4: LOOK UP TRANSFORMATION RULE (T028G) The core lookup: VGTYP (format) + VGEXT (ext code) + VOZPM (+/-) → VGINT (posting rule) + INTAG (algorithm) Example (HQ Societe Generale): SOG_FR + NTRF + "-" (outgoing) → Rule 102O, Algo 015 SOG_FR + NINT + "+" (incoming) → Rule 111I, Algo 000 Example (Field Office): XRT940 + NTRF + "-" (outgoing) → Rule SUBD, Algo 015 XRT940 + NCHG + "+" (incoming) → Rule SUBC, Algo 015 (ALL XRT940 codes → SUBC/SUBD, always algo 015!) STEP 5: APPLY POSTING RULE → GL ACCOUNTS The posting rule determines WHICH GL accounts get debited/credited: Rule 102O (Outgoing clearing on sub-bank): DEBIT: 11xxxxx (BANK_SUB) ← sub-bank clearing account CREDIT: 10xxxxx (BANK) ← main bank account Post Type: 4 (Clear debit G/L) Doc Type: Z1 Rule 101I (Incoming simple post): DEBIT: 10xxxxx (BANK) ← main bank account CREDIT: 11xxxxx (BANK_SUB) ← sub-bank account Post Type: 1 (Post only, no clearing) Doc Type: Z1 STEP 6: ALGORITHM DETERMINES CLEARING Based on INTAG, SAP tries to automatically clear the sub-bank item: 000 = No clearing attempt (just post) 001 = Standard matching 013 = Match by check number 015 = Match by ZUONR (assignment field) ← MOST COMMON 019 = Match by DME file reference If algo 015: SAP reads MT940 Tag 86 (note-to-payee text) → Search strings extract payment document number → Matches against open items on 11xxxxx by ZUONR → If match found: AUTO-CLEAR (item moves to BSAS) → If no match: item stays OPEN on 11xxxxx for manual FEBAN STEP 7: BUSINESS AREA DETERMINATION During posting, the BA substitution fires: GGB1 → YRGGBS00 → YTFI_BA_SUBST (BUKRS + BLART + HKONT range → GSBER) Fallback: YBASUBST (legacy 1:1 mapping) If clearing: BA inherited from the matched offsetting item Result: FI document posted with correct Business Area (GEF/PFF/OPF/MBF)

🏛 Bank Classification Groups — the strategic dimension (why A/B/C/D matters beyond OT83)

The A/B/C/D taxonomy is not just a routing label for this OT83 change. It is the formal name for a classification that has existed at UNESCO for years — encoded in conventions (GL number scheme, FBZP exclusion rules, fund accounting structure) but never declared in any single SAP table. The OT83 work below is the first time the classification becomes machine-readable in SAP via VGTYP. Treasury has no documentation of this taxonomy — but the system itself proves it has existed for a long time.

🧭 How Bank Groups connect to the new GLs — the routing chain (read this first)

Treasury's groups (A=Current, B=Savings, C=ASHI, D=Nessim) do not exist in SAP as a field. They exist in Treasury's Excel. To make SAP act on a group, we ride the VGTYP (Transaction Type) — a pure label that EBS uses as the entry point into the posting-rule chain.

For the deeper "why" behind the classification (IPSAS 39, donor restrictions, the hidden HKONT numbering convention, where the classification de-facto already drives FBZP / F.52 / FMDERIVE) → see Bank Classification Groups — strategic dimension below.

⚡ Most important fact in this whole tab
T028V (the VGTYP catalog) has only two columns: VGTYP + Name. There is no bank reference, no group reference, no posting-rule reference inside it. It is just a label.

The binding from a real bank account to a VGTYP lives one level down in T028B (Bank Accounts) — one row per bank, with the column VGTYP pointing to the catalog entry. The act of "assigning Group A to TR_TRNFA" = updating each Group A bank's T028B row to point at the new VGTYP. T028V just gives that label a name.

🧮 Why VGTYP and not Bank Account directly?

Question Answer
Could we route by individual bank account? No. T028G is keyed by VGTYP, not by bank account. The posting rule resolution always goes through VGTYP. So to differentiate, we need a different VGTYP — there is no per-bank override.
Then why doesn't SAP just put VGTYP on each bank? It does — that's T028B. Layer 1. The fact that T028B.VGTYP exists is the entire mechanism. The "label" (T028V) just gives that value a name for reporting.
Could we add a column to T028V to bind groups? No. T028V is SAP-standard (only VGTYP + Name). Plus we don't need to — the binding lives in T028B as one row per bank, which is finer-grained than per-VGTYP would be.
What if two banks must behave differently inside Group A? Then they need different VGTYPs (e.g., one on TR_TRNFA, the other on a new TR_TRNFA2). The pattern scales — each new differentiation = one new VGTYP + one T028B reassignment + maybe one T028G clone.

📖 OT83 step-by-step walkthrough — every screen, with Purpose + Impact

The 6-folder dialog above shows the structure; the screens below show the live UNESCO config at each step. Each step explains WHY this configuration exists (purpose) and WHAT BREAKS IF IT'S WRONG (impact). Read top-to-bottom for the full mental model.

🚪 Step 0 · Entry — Determine Work Area

What this is The scope selector. SAP segregates EBS configuration by application (0001=EBS, 0002=Lockbox, 0004=G/L Interest Scale used by F.52) and by chart of accounts. UNESCO's only EBS chart is UNES.
Purpose Tells SAP which configuration scope to load. The same OT83 transaction can edit multiple applications and multiple charts — this popup picks one.
Impact if wrong If you pick application 0004 by mistake, you'll be looking at G/L Interest Scale (F.52) config, not EBS. If you pick a different chart, you won't see UNESCO's symbols at all. Wrong scope = invisible mistakes.
Connects to Every subsequent screen filters by these two values. T033F.ANWND='0001' and T033G.KTOPL='UNES'+ANWND='0001' come from here.

📛 Step 1 · Create Account Symbols (the catalog of names)

What this is A pure naming catalog. Each row defines a symbol (e.g. INTEREST_REC) with a description (e.g. "INTEREST RECEIVED"). No GL is set here — this is just the dictionary of names that other screens will reference.
Purpose Decouples the abstract concept ("interest received") from the actual GL number. This abstraction is what lets the same posting rule (111I = "incoming GL interest") fire for hundreds of bank accounts across all chart-of-accounts variants — each chart maps the symbol to its own GL.
Impact if wrong If a symbol is missing from this catalog, no posting rule can reference it → SAP throws an error at posting time ("Account symbol X not defined"). If a symbol is named ambiguously (e.g., two symbols both called "Interest"), human error in step 4 (Define Posting Rules) becomes likely.
UNESCO discoveries
  • INTEREST_REC + INTEREST_PAID — the two symbols at the heart of INC-000008088
  • TSF_CLEARING — newly visible: TRANSFER CLEARING (used for sweep / pooling movements)
  • 5 OFFSET variants (BANK ELECTRO, BANK D/B, BANK FX FO, BANK MANUAL, SUB BANK, TECH SUB) — UNESCO has fine-grained offset accounting
  • UNDP country symbols (UAE, UAF, UAL, UAM, UAO, …) — each maps to a 9-digit country-specific cash GL (out of scope for INC-000008088)

🎯 Step 2 · Assign Accounts to Account Symbol — THE GL ROUTING LAYER (where INC-000008088 changes)

What this is The actual GL mapping. For each (Account Symbol, Account Modifier, Currency) combination, define the GL via a 10-character mask where + = copy from bank GL and digits = literal. E.g. +++7044011 with bank GL 0001008011 resolves to 0007044011 = GL 7044011.
Purpose This is where SAP decides where money goes. The mask design lets you do "smart" routing — e.g., BANK_SUB +++11+++++ means "take the bank's master GL and substitute digits 4-5 with 11" so each bank gets its OWN sub-bank account automatically. INTEREST_REC's hard-coded literal mask (no wildcards in positions 4-10) means EVERY bank routes to the same GL.
Impact if wrong Wrong mask → wrong GL → wrong P&L line → wrong financial statements. Today's INC-000008088 is exactly this: the literal "7044011" in INTEREST_REC's mask is too coarse — it lumps savings-account interest with current-account interest with ASHI/Nessim Habif fund interest, all into one catch-all GL. Treasury wants this row split.
The change Path A (single GL): Edit one cell — change INTEREST_REC mask from +++7044011 to +++7044014. Effect: all 26 bank accounts now post savings-interest to 7044014.

Path B (full split): Create new symbols INTEREST_REC_A/B/C/D in step 1, map each to its own GL here in step 2 (+++7044013 / +++7044014 / +++7043014 / +++7043021), then re-bind posting rules in step 4 to use the right symbol per bank group. Affects steps 1, 2, 4, and possibly 6 (if VGTYP also splits).

🔑 Step 3 · Create Keys for Posting Rules (the rule code catalog)

What this is Like step 1, this is a pure naming catalog — but for posting rules instead of account symbols. A rule code is a tiny tag (4 chars: 111I, 102O, SUBC, MDEC, …) that becomes the middleman between (a) what the bank sent in the MT940 file and (b) what GL accounts post.
Purpose Decouples bank-side codes (NTRF, NINT, FCLR — there are dozens, and they vary by bank) from SAP's posting logic. Many banks' "incoming interest" codes (NINT, FINT, sometimes NTRF marked specially) all funnel into rule 111I, which then posts the same way regardless of which bank sent it.
Impact if wrong If a rule code is missing, T028G can't route external codes into it → unmapped bank lines fall through to rule 199I (UNKNOWN POSTING) → end up in FEBAN for manual processing. Each missing code = one workflow that requires a human.
Naming pattern
  • 3-digit + I/O: SAP standard (101I = first I-class incoming; 111I = interest)
  • SUBC/SUBD/SUBE/SUBF: UNESCO-specific generic field-office rules
  • MDEC/MDED, MXXC/MXXD, MXYC/MXYD: money-desk extensions
  • UAEC/UAED, UAFC/UAFD, …: per UNDP country (≈100 codes)
  • TXDO/TXDT/TXWO/TXWT: tax / withholding

⚙️ Step 4 · Define Posting Rules — wire each rule to DR + CR symbols

What this is The posting recipe for each rule. Defines: which symbol on the debit side + which posting key (40=GL DR, 50=GL CR), which symbol on the credit side + which posting key, the document type, and the posting type (1=post only, 4=clear debit, 5=clear mixed, 8=clear sub-ledger).

Posting type cheat sheet
  • 1 — Post only, no clearing attempt (used by 101I/O, 111I/O, 199I/O — most common)
  • 4 — Clear debit GL (used by 102O — outgoing with sub-bank clearing)
  • 5 — Clear mixed (used by 102I — incoming with sub-bank clearing)
  • 8 — Clear credit sub-ledger (used by 201I/O — customer payment with sub-ledger match)

🏦 Step 5 · Create Transaction Type (VGTYP — bank format catalog)

What this is The catalog of "bank format profiles". Each VGTYP groups bank accounts that share the same statement format and posting conventions. UNESCO has 23 distinct VGTYPs across all BUKRS; UNES uses 8 of them.
Purpose Some banks send NTRF for both incoming and outgoing transfers; others use NCRD vs NDBT. Some send check codes as NCHK; others as CHKD. The VGTYP is the "bank dialect" — it lets step 6 (T028G mapping) translate that bank's specific external codes into the universal internal rules (101I, 111I, etc.) defined in step 3.
Impact if wrong If you assign a bank account to the wrong VGTYP, every external code that bank sends gets translated as if it came from a different bank → wrong rule fires → wrong GL posting. VGTYP misassignment is one of the most-frequent sources of EBS posting errors at UNESCO field offices.

🔄 Step 6 · Assign External Transaction Types → Posting Rules (the bank-dialect translator)

No screenshot in this batch — this folder backs table T028G (1,025 mappings in P01). The user did not capture it because the previous review covered it (it's the busiest table). Summarised below.

What this is For each VGTYP, the per-external-code mapping: (VGTYP, external code, +/- sign) → internal rule code + algorithm. E.g., (TR_TRNF, NTRF, +) → (102I, algo 015): when a TR_TRNF bank sends NTRF on a credit line, fire rule 102I and try to clear via ZUONR matching.

🔗 Step 7 · Assign Bank Accounts to Transaction Types (the per-account binding)

What this is The per-account binding row. For each (Bank Key, Bank Account) pair, says which BUKRS owns it and which VGTYP it follows. This is the last piece of EBS configuration: once you've defined symbols, posting rules, and bank dialects, you tell SAP "here are my actual accounts and here's how to treat each one".
Purpose The entry point of the EBS chain at runtime. When a statement arrives, SAP looks up (BANKL, KTONR) here to find which BUKRS + VGTYP to use. This determines everything downstream.
Impact if wrong If a row is missing → SAP rejects the statement (cannot post). If VGTYP is wrong → all external codes from that account translate via the wrong dictionary → systematic posting errors. Statement arrives → look up (BANKL, KTONR) in step 7's table (T028B) → BUKRS, VGTYP 2. Read each statement line's external code → look up via step 6's table (T028G) → internal rule + algorithm 3. For that rule, look up step 4's table (T033F) → DR symbol + CR symbol + posting keys 4. For each side, look up step 2's table (T033G) → resolve symbol + currency to actual GL via mask 5. Post the document. For INC-000008088 (savings interest → 7044014): → Path A: edit ONE row in step 2 (INTEREST_REC mask: +++7044011 → +++7044014) → Path B: edits in steps 1, 2, 4 (new symbols + new posting rules + wire them) steps 5, 6, 7 untouched (banks already bound correctly)
Why is edit-time order different from run-time order? Because catalogs (steps 1, 3, 5) must exist before they can be referenced. SAP enforces this with FK-style constraints — you cannot save a step-2 row pointing to a non-existent symbol from step 1.

The +++ wildcard mechanism

Each character in the mask (T033G.KONTO) is either a literal digit or a + wildcard. A + copies the corresponding character from the bank's master G/L account (T012K.HKONT). Literals are fixed.

Example — INTEREST_REC posting on bank GL 0001008942 (CIC01-EURD4) Mask: +++7044011 Bank GL: 0001008942 ↓↓↓↑↑↑↑↑↑↑ Character: pos 1-3 = "+" → copy from bank GL: "000" pos 4-10 = literal: "7044011" Result GL: 0007044011 = GL 7044011 (10-digit zero-padded form) Implication: Since EVERY UNESCO bank GL starts with "000", all EBS interest credits resolve to GL 7044011 today, regardless of which bank. The mask is bank-agnostic.
