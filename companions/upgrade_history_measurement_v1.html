What this measures

An executed SAP upgrade leaves a forensic trail. This companion measures it from three P01 tables, read-only over SNC/SSO: UVERS (release/EhP upgrade history), PAT03 (every support package + its implementation date), and CVERS (the current stack = the endpoint).

P01 has had one release upgrade (EhP8, 2017) and a roughly annual cadence of Support-Package stacks since. "The last 3 upgrades" = the 3 most recent full SP stacks.

Verdict

• By patch volume, June 2026 is the biggest maintenance event since EhP8 (275 patches, 59 components, SAP_BASIS +6 levels) — it absorbed the skipped 2025 cycle (~23-month gap).

• But by operational impact, July 2024 was the painful one: 503 SPAU adjustments (3.6 per support package) vs 343 for 2026 (1.6 per SP). Volume of SAP patches does not predict how much UNESCO custom code breaks — that depends on whether SAP changed the specific objects UNESCO had modified.

• The SP import itself is a near-constant ~6–8 h regardless of stack size; the difference between upgrades is ~2 h. The real time-and-effort cost lives in SPAU rework, not the import window.

• The June 2026 run is the same "Upgrade 2026" that was blocked in April by 7 open P01 customizing requests (see upgrade_2026_v01_open_customizing_requests.html); resolved, imported 2026-06-07.

The point: volume ≠ impact

An upgrade's operational cost is not the number of patches. It is two things: (1) how long the import runs (the time window the system is busy / down), and (2) how much custom code must be re-adjusted afterwards — the SPAU/SPDD rework. Both are measured below from TPALOG (per-step import timestamps) and SMODILOG (the modification log).

How SPAU was attributed (method)

P01 SMODILOG holds 9,852 logged modifications, of which 5,809 are SPAU-relevant (flag set). Each SPAU-flagged modification carries the TRKORR of the transport that adjusted it; that transport is dated via E070.AS4DATE and bucketed to the upgrade month. So "503 adjustments in 2024-07" = 503 SPAU-flagged modifications whose adjustment transport was released in that upgrade window.

Full SPAU history (all upgrades): EhP8 2017-04 = 1,219 · 2022-04 = 515 · 2024-07 = 503 · 2026-06 = 343 · 2023-06 = 233 · 2021-04 = 169. The custom-code burden has trended down since the 2017/2022 peaks.

Where the upgrade fragility lives — the 502 objects re-adjusted in July 2024

The heaviest upgrade (2024-07) forced 502 SPAU adjustment records across 187 distinct objects, all re-applied by N_MENARD (the implementation partner) during the import. These are SAP-standard objects UNESCO modified in place — so every time SAP ships a new version of them, the modification collides and must be re-adjusted by hand. So what — how to stop paying this every upgrade

• The 502 adjustments are not random — they are the same modified objects re-breaking each cycle. The 2024, 2023 and 2022 upgrades all re-adjusted the same HR/Payroll core.

• The lever is clean-core refactoring: move the most-recurring in-place modifications (the PBUN payroll classes, the infotype objects) to enhancement techniques — BAdIs, enhancement spots, append structures — so SAP's new versions no longer collide with them.

• Converting just the top ~20 recurring HR/Payroll objects would remove a large share of the per-upgrade SPAU burden — turning a 500-adjustment manual task into a fraction of it, and de-risking every future upgrade and the eventual S/4HANA move.

Honest limits of this measurement

Import time is measured; full SUM downtime is not. The 5.7–8.1 h figures are the SP-queue import (SAPK* steps) from TPALOG.TRTIME on the main import day — the real busy window for applying the packages. The total technical downtime of a SUM-driven run (shadow system, EU_IMPORT, post-processing) is wider and lives in the Software Update Manager logs (UPGANA.XML / phase log) at OS level — not RFC-readable. PAT03.IMPLE_TIME alone understates duration: for 2023/2024 it is just the SPAM commit stamp (all patches within ~2.5 min), which is why timing was taken from TPALOG, not PAT03.
SPAU attribution buckets SMODILOG SPAU-flagged modifications by their adjustment transport's E070.AS4DATE. This dates when each custom object was re-adjusted; it does not capture manual effort-hours per object (not recorded in SAP). The object-level list (which classes/DDIC objects) is in the smodilog Gold DB table if you want it per upgrade.
