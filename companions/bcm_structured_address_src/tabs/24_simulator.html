🧪 Testing Simulation — V001 testing methodology in 4 complementary layers

V001 is validated by 4 layers of testing — each layer catches a different class of error, runs at a different speed, and has a different fidelity. The Python simulator (claim 105) is layer 1; SAP-native tx DMEE Test Data (manual + history-replay) are layers 2 and 3; D01 F110 integration is layer 4. None of layers 1–3 require V001 activation anywhere — they are entirely build-time validation that retires most V001 design risk before any Phase 5-style activation.

Recommended order through Phase 3 / Phase 4: layer 1 first (catch design errors at code-review speed) → layer 2 second (sanity-check the simulator's predictions in real SAP for a few cases) → layer 3 third (top-15 scenarios = 94.5% volume coverage in ~30 min total) → layer 4 fourth (final integration). The earlier the layer, the cheaper the discovery — issues caught at layer 1 cost seconds; the same issues caught at layer 4 cost 30 minutes plus a transport rework.

Strategic implication: layers 1–3 are 100% build-time validation. They retire V001 design risk WITHOUT touching the SAP version-management lifecycle (no Generate Version snapshot, no Activate Version, no Workbench transport activation). Layer 4 is where D01-side activation enters — and the SAP-correct deployment lifecycle (snapshots, atomic activation = overwrite, Version-Management retrieve for rollback) only starts mattering at layer 4 and Phase 5. By the time Phase 5 cutover arrives, V001 design risk is already retired by layers 1–3 — the cutover is mechanical, not exploratory.

Layer 1 — The Python simulator (claim 105)

A pure-Python re-implementation of the DMEE engine that reads real P01 payment data from the Gold DB, renders V000 + V001 XML, and validates against ISO 20022 XSDs. Validated 794 production cases × 3 schemas = 2,382 PASS / 0 FAIL. Used for fast design iteration during V001 build — issues caught here cost seconds to fix.

Why simulate before touching SAP at all?

Most SAP projects test by deploying ABAP to a sandbox client, running F110 with synthetic data, and inspecting the output XML. That works, but it has three drawbacks: (1) it requires a transport, (2) it requires sandbox SAP authorisation, (3) running 794 test scenarios serially through F110 takes hours per run. The Python simulator solves all three: it is pure Python, runs entirely on local Gold DB data, and renders V000 + V001 pain.001 XML in seconds per scenario. We can iterate on the V001 design at the speed of code review, not the speed of SAP transports.

What the simulator actually does

The simulator implements every layer of the SAP-side pipeline in Python: it reads real P01 payment data from the Gold DB (REGUH_FAST + REGUP + LFA1 + ADRC), follows the same field mappings the DMEE tree would follow, builds V000 (current) and V001 (proposed) XML side-by-side, then validates both against the official ISO 20022 XSDs. The simulator is correctness-equivalent to F110 + DMEE for the address-tag scope — and that equivalence is itself a tested invariant (claim 105: 794/794 PASS on both pain.001.001.03 and pain.001.001.09 schemas). Layer 1 limit: the simulator is Python — any SAP-engine quirk Python doesn't reproduce will not be caught here. That gap is exactly what layers 2 and 3 close.

What this layer enables for V001

Three high-leverage outcomes: (1) design questions that would otherwise need bank confirmation (e.g., "does the bank accept the V001 tag layout?") become testable locally — the simulator validates against pain.001.001.09 (the CBPR+ Nov 2026 schema) so we know V001 is forward-compatible without sending a single test file; (2) per-tree per-vendor edge-cases (UltmtCdtr Worldlink, name-overflow, missing house-numbers) get exhaustive coverage in seconds; (3) the simulator becomes the regression baseline for layer 4 testing — when D01 F110 produces a real V001 XML, we diff it against the simulator's expected output to catch any unexpected SAP-side behavior.

F110 history replay via DMEE Test Data — SAP-native testing complementary to the Python simulator

⚠ KEY CONSTRAINT — DMEE Test mode tests ONLY the Active version

tx DMEE menu exposes "Format tree → Test active version" (F8). There is no "Test maintenance version" menu option. This means engine-level testing splits into two non-symmetric paths:

  • V000 testing (Phase A) — runs anywhere (D01/V01/P01) via F8 against the production active state. No activation needed. No risk. Proves L1 (Python simulator) ↔ L2 (SAP engine) equivalence on V000.
  • V001 testing (Phase B) — D01 ONLY — V001 cannot be tested in isolation via F8. To run F8 against V001 content, V001 must FIRST be activated (which per SAP-correct lifecycle overwrites V000 with V001 content). Therefore V001 testing requires the full snapshot+activate+test+rollback ritual: (a) Generate Version on D01 V000 → archives to V002 (rollback enabler); (b) Activate V001 → V001 content becomes the new D01 V000; (c) F8 Test active version → output is V001 engine output; (d) Retrieve V002 from Version Management → Activate → original V000 restored.

Implication for the 4-layer methodology: Layer 2-3 as a "test V001 without activation" path does NOT exist for engine-level validation. What L2-3 actually delivers is engine-level validation of V000 (without activation, in any system). V001 engine testing requires Layer 4 (D01 with V001 activated). The Python simulator's V001 predictions are trusted transitively once L1 V000 ≡ L2 engine V000 is empirically confirmed for the same scenarios.

The Python simulator above is one way to validate V001 without F110. SAP itself ships a second, complementary mechanism that runs the real DMEE engine against manually-entered test data — tx DMEE → Format tree → Test active version (F8) — the "DMEE Test Data" screen. The screen is the entry point of stages ⑤–⑦ in the E2E Flow chain: it accepts the same buffer structures (FPAYHX / FPAYH / FPAYP) that F110 + Event 05 populate at runtime — but populated manually by the operator. Per the constraint above, this F8 path tests whichever version is active at the moment of execution.

unesco_dmee_test_data_input_buffers.png — DMEE Test Data screen showing the 3 input grids: FPAYHX (formatting of payment data), FPAYH (data for payment), FPAYP (data for paid items). Each grid accepts manual row entry; the column names visible (ISO Code / Account No / Name / Street / Bank city / IBAN / SWIFT/BIC / Amount / Crcy / etc.) ARE the SAP-standard DDIC fields of these structures. What is NOT visible by default is UNESCO's append-structure extensions — the 25 custom Z-fields in CI_FPAYHX (ZSTRA, ZBSTR, ZBORT, ZBPST, ZLAND, ZORT1, ZPSTL, ZREGI, ZLISO, ZPFST, ZPLOR, etc., per claim 67) that V001 references for UltmtCdtr Worldlink and CdtrAgt cases. Those custom fields exist at the table level but require scrolling/expansion (or the operator using "More fields" in the test screen layout) to populate. This visual boundary is itself useful: it tells you which V001 bindings reference SAP-standard fields (low-risk, universally available) vs custom append fields (UNESCO-specific, need explicit handling in test scenarios).
The strategy — replay F110 history into the test screen

Combine two artifacts UNESCO already has: (a) F110 history persisted in REGUH / REGUP / REGUT (every payment ever produced is reconstructable from these tables); (b) the same tx DMEE Test Data input shape on the screen above. Pick any historical F110 batch — for example, the SEPA Payroll run from 2025-Q4 with 103,126 line items (scenario #2 of the 81-scenario coverage above). Reverse-engineer the FPAYH / FPAYHX / FPAYP rows for one of those payments from REGUH/REGUP, paste them into the DMEE Test Data screen, switch to V001 view, click Test, and SAP runs the real DMEE engine against your manually-pasted buffers and renders the V001 XML. You see exactly what F110 would have produced for that historical payment under V001, without F110 ever executing.

Why this matters for the change strategy
  1. Validates V001 against real production patterns without F110 — pick the top-15 scenarios (94.5% of volume per the table below), reconstruct one representative payment per scenario from REGUH/REGUP, paste into Test Data, simulate. If the V001 XML output is structurally correct and schema-valid, V001 is validated against 94.5% of production volume — without ever running F110 in any system.
  2. Reproduces specific bank-rejection scenarios deterministically — when Marlies's analysis or a bank reports a specific defect ("payment X to vendor Y to bank Z was rejected because..."), find that exact REGUH record, reconstruct its FPAYH/FPAYHX/FPAYP, paste into Test Data, run V001 → see if V001 still produces a problem-XML or fixes it. Same input + V000 vs V001 = direct A/B comparison.
  3. Field-visibility audit comes for free — when reconstructing FPAYHX, every field your V001 design references via MP_SC_FLD must be populated. If the field is in the visible part of the test screen, it is SAP-standard and universally available. If it is hidden in the append-structure section (Z-fields), that binding depends on UNESCO's CI_FPAYHX customization and won't work in any other UNESCO-like environment without the same extension. This audit is a derivative output of the testing exercise: the V001 design's portability gets characterized as a side effect.
  4. Complementary, not duplicative, to the Python simulator — the Python simulator catches design errors (matrix-spec issues, wrong byte offset, wrong source-bind structure, missing DMEE_TREE_COND). The DMEE Test Data approach catches engine-implementation differences (anything Python implements differently from the SAP-standard DMEE engine — e.g., XSLT post-processing nuances on CITI tree, or per-node EXIT_FUNC behavior). Use both: simulator first for fast iteration, DMEE Test Data for a SAP-native confirmation pass on the top scenarios.
  5. V000 testing in any system without activation; V001 testing in D01 only with activation ritual — per the F8 KEY CONSTRAINT above, the Test Data screen runs the Active version. V000 (current production) can be tested in D01/V01/P01 with zero side effects (no activation, no F110 file, no BCM batch). V001 testing requires Layer 4: Generate Version snapshot → Activate V001 in D01 → F8 Test → Retrieve snapshot → Activate to rollback. The "no activation needed" property applies only to V000 testing.

Why the alignment matters — three correctness properties stacked

Running the same 3-cases-per-template at every layer validates three independent correctness properties on the same input space:

LayerWhat this layer is validatingWhat the alignment buys
L1 — Python simulator"V001 design produces schema-valid pain.001 against XSD .03 and .09" — i.e. schema-correctness of the designCatches matrix-spec errors at code-review speed (seconds per scenario). Output: 2,382 PASS confirms the design is schema-valid in principle.
L2-3 — DMEE Test Data"SAP's actual DMEE engine, given the same input buffers, produces schema-valid output that matches the Python simulator's prediction" — i.e. simulator-vs-SAP equivalence per scenarioIf L2-3 output ≡ L1 prediction for every case → claim 105's "correctness-equivalent" assertion is empirically proven, scenario by scenario. If any case differs → that is a SAP-engine quirk Python missed; we know about it before Phase 5 instead of in production.
L4 — D01 F110"The full upstream chain (F110 + SAPFPAYM + Event 05 + DMEE + BCM) produces the same XML the test layers predicted" — i.e. integration-correctness of the chainCatches issues that span F110/SAPFPAYM/BCM, not just DMEE. Top-K scenarios is sufficient — we don't need 794×3=2,382 F110 batches; we need ~15 representative ones because L1-L3 already validated the DMEE layer exhaustively.

The alignment principle in one sentence: same 4 templates × same 3 cases × same 794 sample inputs at L1, L2-3, and a sampled subset at L4. Coverage doesn't fragment across layers — it's the same matrix evaluated by progressively higher-fidelity validators. Anomalies at any layer reveal a specific class of error (design / simulator-equivalence / integration) without ambiguity. This is what makes the methodology operationally tight rather than just "we test multiple ways".

Practical Phase 3 sequencing: layer 1 already done (claim 105). For layer 2-3 V000 baseline runs: prioritize the top-15 scenarios (94.5% volume coverage) × 4 templates × 1 case (V000) = 60 DMEE Test Data runs (~5 min each = ~5 hours of focused work, splittable across operators), no activation needed. For layer 4 V001 runs: top-15 × 4 templates × V001 activation cycle = 60 cases × ~30 min each = ~30 hours, in D01 only with snapshot+rollback ritual. Total Phase 3 effort = days of focused testing, not weeks of D01 cycles.

Pay-type axis — orthogonal dimension connecting to PPC system

The pay_type column (derived from FPAYH-DORIGIN[0:2]) takes 3 values used by the PPC dispatcher (YCL_IDFI_CGI_DMEE_UTIL::GET_TAG_VALUE_FROM_CUSTO, claim 99):

  • O (Other) — vendor invoice payments. Most common (~70% of in-scope).
  • P (Payroll) — DORIGIN starts with HR. SEPA pm=S split between O+P (#1+#2 of top 15) is purely a PPC-routing concern, not a tree-design concern — V001 nodes don't differentiate.
  • R (Replenishment) — DORIGIN starts with TR. Includes Worldlink BRL (#4 of top 15). PPC tags fire here for the 9 PPC countries.
Operational consequence for V001 risk model

Every V001 risk question is bounded by "which of the 81 scenarios?" instead of "what if some unknown payment breaks?":

  • Phase 3 unit test stratifies by the 81 — top 8 cover >88%, top 15 cover 95%
  • Phase 4 UAT needs only ~5-8 scenarios for bank end-to-end validation; simulator already proved the other 73 are schema-equivalent
  • Cutover monitoring (Phase 5) — daily schema-fail rate per scenario class; investigation scope bounded
  • Regression baseline — re-run scenario_discovery + simulator after V001 deploys for byte-level V000-vs-V001 diff per scenario class
