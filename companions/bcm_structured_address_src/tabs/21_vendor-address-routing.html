Vendor Address Routing — Y_FI_DMEE_ADR · KTOKK-agnostic, PA0006-first [deployed v6 · 2026-05-08 · D01]

↶ Sibling of Tree 1 · SEPA (FM is wired into V001 SEPA Cdtr/PstlAdr + Dbtr/PstlAdr exit nodes only — CGI uses BAdI YCL_IDFI_CGI_DMEE_FALLBACK with a different convention). Knowledge anchor: vendor_address_routing_by_ktokk.md.

Why this section exists — root cause

UNESCO maintains multiple LIFNR records per real-world entity with different KTOKKs, and the meaning of ADRC.STREET depends on the account group. For staff (KTOKK=SCSA) ADRC.STREET is a department code like BFM/FAS/PAY or ADM/DIT/MIS/FBS — not a real address. Any system that reads ADRC blindly emits the dept code as the street. SEPA banks reject this. The fix lives in the custom DMEE exit FM Y_FI_DMEE_ADR (NOT in standard, NOT in Nicolas's BAdI — see rule feedback_only_modify_our_own_code).

Marlies SPRONK is one real person with one real home address but appears as 4 different LIFNRs in LFA1, each linked to a different ADRC entry depending on the business context (staff payroll, HQ link, personal, inter-company). The same is true for Simona BERTOLDINI and any UNESCO employee paid via SEPA.

Decision matrix — where the FM reads the address

KTOKKSource for SEPA / outputWhy

Implementation choice: rather than dispatch on KTOKK explicitly (v5 design — failed for BERTOLDINI on UNES), v6 attempts PA0006 SUBTY='1' first, regardless of KTOKK. If found → employee path (PA0006 fields). If not found → vendor path (ADRC fields). This is KTOKK-agnostic: it correctly handles any LIFNR that maps to a PERNR (NUMC8 cast), no matter which account group F110 happened to pay against.

Branch detection — Cdtr vs Dbtr

The FM serves both Cdtr/PstlAdr (beneficiary) and Dbtr/PstlAdr (paying co) leaves. It walks 2 hops up via DMEE_TREE_NODE.PARENT_ID to identify the grandparent's TECH_NAME (Cdtr or Dbtr). Cdtr branch runs the PA0006-first detection. Dbtr branch reads T001-ADRNR by FPAYH-ZBUKR → ADRC (paying co always has a real address — KTOKK pattern does not apply).

Affected systems beyond V001 SEPA — audit candidates

The KTOKK/ADRC convention is system-wide, not SEPA-specific. Any UNESCO output that reads ADRC of LIFNR without going through PA0006 will print the dept code for staff vendors. Open audit candidates:

  • ☑ SEPA Credit Transfer XML (V001 SEPA_CT_UNES) — fixed by v6
  • ☑ CGI XML CT formats (Cdtr/PstlAdr nodes) — Nicolas's BAdI uses different routing; CGI is OK for Dbtr/Cdtr but CdtrAgt is unrelated
  • ☑ CITI XML formats — Cdtr already structured, but check if it reads ADRC blindly
  • ⚠ Avisos de pago (RFFOAVIS_FPAYM) — likely shows dept code as street
  • ⚠ F110 confirmation prints / SAPF110V — likely same defect
  • ⚠ BCM batch printout — likely same defect
  • ⚠ Bank statement reconciliation reports — depend on which path they read
  • ⚠ Treasury cash forecasting — probably uses ADRC; may be OK for non-SCSA only

Recommended pattern: build a centralized helper FM Y_GET_VENDOR_ADDRESS(LIFNR) that returns the real address based on PA0006-first detection, and replace ad-hoc ADRC reads across UNESCO custom code. Tracked as KU.
