V001 Change Matrix — node-by-node design specification

Why this matrix exists

Saying "we will add structured address tags to 4 DMEE trees" is a high-level statement. Saying "we will create node N_NEW_001 as child of N_5649723900 with NODE_TYPE=ELEM, MP_SC_TAB=FPAYHX, MP_SC_FLD=REF01, MP_OFFSET=0, LENGTH=60" is what M_SPRONK can actually configure in DMEE Tx. This matrix is the bridge between the two — every node, every condition, every TFPM042FB row, every ABAP line of V001 is enumerated as one row, with all the fields needed to execute the change without inventing values. No row is speculative; every PARENT_NODE_ID and every source-field reference is verified against the real P01 tree state (1,975 nodes already extracted).

How to use this matrix

Read it as the build instructions for Phase 2. Each row maps to a single config click in DMEE Tx (or a single line of ABAP for Pattern A). When M_SPRONK opens DMEE → /SEPA_CT_UNES → V001 → Edit, she can use the Action, Parent Node, Tech Name, Source, MP_OFFSET, Length columns directly to fill in the SAP screens. There is no judgment-call space here on purpose: the design is locked, the values are known, the work is mechanical.

The matrix totals 27 rows split across 8 transports — and that 27/8 split is itself meaningful. Claim 102 established that 81.8% of UNESCO's historical DMEE transports touched ≤3 objects (the "surgical pattern"). V001's 8 transports averaging ~3 objects each puts the work squarely inside that historical envelope. This is not a project asking the team to do something operationally novel; it is a project executing the team's normal change cadence at the normal scale.

Design decisions — embedded in matrix rows 1-8 (TIER_1 evidence)

After D01 V001 RFC verification (2026-05-06) the matrix design choices crystallized against ground truth. Three architectural decisions and their evidence anchors:

Decision A — CV_RULE = CL RP    X (Dbtr) / CLURP    X (Cdtr) — 10-character positional flag

CV_RULE is a fixed 10-character positional string, not space-separated tokens. Each position controls one transformation that DMEE applies to the value before writing to XML. Spaces are significant: CL RP X ≠ CLRPX ≠ CL RP X.

PosCharNameWhat it does
1CCompressRemoves leading/trailing spaces from value. "  Place de Fontenoy  " → "Place de Fontenoy"
2LLeft-justifyAligns value at field start; pads right with spaces if value is shorter than slot
3U / blankUpper-caseConverts to CAPS. Cdtr uses U (vendor data is mixed case → force consistency); Dbtr leaves blank (UNESCO HQ data already uppercase)
4RReset on initialMarks field as "considered empty" if value is initial after C+L (works with empty-suppress condition logic)
5PPrint/PadFor chars: print field even if empty post-Reset (override of R suppression). Combined with R = "let DMEE_TREE_COND condition decide", not automatic suppress
6-9(blank)reservedSAP reserves these positions; UNESCO leaves blank
10XUNESCO custom flagNon-SAP-standard. Customer Z-namespace marker. Likely XSLT-aware (CITI tree has XSLT post-processor) or XML-output mode flag. 100% consistency across all UNESCO leaves cross-tree → mandatory for new V001 leaves

Decoding the SEPA V001 patterns:

  • CL RP    X → C + L + (no U) + R + P + (4 spaces) + X — used for Dbtr V001 leaves + existing AdrLine ORT1Z
  • CLURP    X → C + L + U + R + P + (4 spaces) + X — used for Cdtr V001 leaves + existing AdrLine ZPFST/ZPLOR
  • CL       X → C + L + (no U/R/P) + (4 spaces) + X — used for CITI Dbtr-1 leaves (XSLT handles empty-suppress globally)

Anchor: verified via dmee_tree_node_p01.csv extraction 2026-05-06. SEPA Dbtr AdrLine N_4946758140 has CL RP    X in production today — V001 Dbtr leaves mirror this. SEPA Cdtr AdrLine N_6054982000/N_6343458710 have CLURP    X — V001 Cdtr leaves mirror this.

Decision B — BldgNb maps to HOUSE_NUM slot (offset 100, len 10), NOT BUILDING slot (offset 60)

Earlier matrix versions had BldgNb at offset 60 length 20 (the BUILDING slot in CM005 layout). RFC verification of CGI N_8824498030 production pattern revealed UNESCO uses offset 100 length 10 (the HOUSE_NUM1 slot, CM005 line 97).

SlotCM005 lineADRC sourceUNESCO HQ dataVendor data (typical)
REF01[60..80] BUILDINGline 94 +60(20) = ls_adrc-buildingADRC.BUILDING(empty)often empty (only ~31% have building name per Phase 0 Finding A)
REF01[100..110] HOUSE_NUMline 97 +100(10) = ls_adrc-house_num1ADRC.HOUSE_NUM1"7" (Place de Fontenoy)typically populated (street number)

If we read BUILDING slot for <BldgNb>, UNESCO HQ payments produce empty BldgNb (suppressed → bank loses house number "7"). Reading HOUSE_NUM slot produces <BldgNb>7</BldgNb> ✓. Anchor: CGI N_8824498030 production pattern (RFC-verified 2026-05-06) uses offset 100; CM005 ABAP line 97 confirms slot semantics.

Decision C — Ctry + AdrLine UNCHANGED in V001 (hybrid output accepted)

Existing <Ctry> and <AdrLine> nodes are NOT modified by V001. After cutover, output XML contains both the new structured leaves (StrtNm/BldgNb/PstCd/TwnNm) and the original AdrLine + Ctry. ISO 20022 pain.001.001.03 schema permits both coexisting; banks may accept hybrid for now and tighten in CBPR+ Nov 2026.
