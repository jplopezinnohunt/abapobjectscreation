Phase 0 — Discovery & 100% Code Inventory (COMPLETED · 2026-04-24)

Why "100% inventory" before any design

Phase 0 set a hard rule: no design decision without evidence. UNESCO's payment XML pipeline has been touched by 8 authors over 10 years; new contributors typically see only the visible parts (the DMEE tree + the BAdI they touch) and miss the customizing tables, exit functions, and event modules behind the scenes. Phase 0's job was to enumerate everything — every Z-class, Y-include, customizing entry, Event 05 wrapper, byte-buffer field — so V001 design starts from a verified inventory rather than assumptions. The "100%" is not rhetorical: every single MP_EXIT_FUNC reference in the 1,975 P01 nodes was traced to its function module, and every function module was extracted and inspected.

What Phase 0 actually delivered

The Phase 0 outputs become the foundation every later phase rests on: (a) the reference architecture (3 compliance states: Unstructured / Hybrid / Structured), (b) the 31-component map (Components Map tab), (c) the Phase 0 closure report which signed off that no piece of code/config was unaccounted for, (d) the gap-closure memos for each open question. Anything labeled "Phase 0" below is the archive of that discovery — Phase 0 is closed; you are reading the receipts.

How the tree picks the address format — the compound condition on UBISO

Each address node in the CITI tree carries a compound condition (several comparisons of FPAYHX-UBISO joined by AND/OR). UBISO = the beneficiary's BANK country (= REGUH-UBNKS), not the address country. The condition decides whether the node is written → it selects how the Dbtr address is rendered. (Verified V01 2026-06-15.)

Compound conditionOperatorFires when…Output
UBISO = 'US' OR = 'CA' OR = 'PR'OR (any one)bank in US / CA / PRstructured <PstlAdr> (StrtNm·PstCd·TwnNm·CtrySubDvsn·Ctry)
UBISO <> 'US' AND <> 'CA' AND <> 'PR'AND (all)bank in any other countryunstructured <AdrLine> (fallback)
UBISO = 'SE'simplebank in Sweden<PstCd> (+ AdrLine — hybrid)

At first glance this AND looks illogical — "how can a bank be three countries at once?" It can't, and it doesn't have to. The AND does not ask UBISO to hold three values; a bank sits in exactly one country, so UBISO has a single value, and the AND simply runs three separate checks against that one value. For a beneficiary banking in Brazil, UBISO = 'BR', and the engine asks: is BR different from US? yes — from CA? yes — from PR? yes. All three are true at once (a single value can perfectly well differ from three different countries), so the condition holds and the unstructured <AdrLine> is written.

The connector has to be AND because the rule is "none of the three": to be none, the value must differ from the first and the second and the third. A single failing check — e.g. the bank actually is US — collapses the whole condition to false, which is exactly what we want, because US/CA/PR must take the structured branch instead, not the fallback. The "impossible" reading is only true if the operator were =: UBISO = 'US' AND = 'CA' AND = 'PR' would indeed require one value to equal three different countries and could never fire — but the tree uses <> (not-equal), not =. Swapping that one operator turns the condition from "impossible" into the most frequently matched branch of all: every payment to a bank outside US/CA/PR lands here — e.g. all ~8,500 Brazilian payments in 2024. (Formally it is De Morgan's law: NOT(US OR CA OR PR) ≡ (NOT US) AND (NOT CA) AND (NOT PR).)

Reachability — dead-by-DATA, not dead-by-logic (REGUH 2006-2025): only 2 of the 3 branches ever fire with real data. 2024 CITI traffic used only 3 bank countries — US 8,759 · BR 8,472 · CA 1,303. UBNKS is NEVER PR or SE in the whole history, so the PstCd(SE) node and the PR operand never execute today. They are defensive, not removable: the =PR/<>PR pair correctly routes a hypothetical PR-bank payment to PstlAdr (not fallback); deleting them would silently send a future PR/SE payment down the wrong branch. Testing them requires a synthetic vendor (LFBK-BANKS='SE'/'PR').

🔑 The big picture — 2 underlying models, 4-party × 3-format matrix

DMEE trees are XML projections of a shared runtime model (FPAYH/FPAYHX REF buffers/FPAYP/ADRC, filled by Event 05 + exits). There are 2 models: FPM_CGI (shared by CITI + CGI) and FPM_SEPA (SEPA, different). Event 05 is the key: CGI=FI_PAYMEDIUM_DMEE_CGI_05, CITI=/CITIPMW/V3_PAYMEDIUM_DMEE_05 (both fill FPAYHX_FREF); SEPA calls NONE → that is why UNESCO built 17 custom Y_FI_DMEE exits (read ADRC directly).
