What this is & why it matters

At UNESCO, a posting's account-assignment fields (Business Area, Cost Center, Fund, Fund Center, payment method, office tag) are rarely what the user typed — they are rewritten by a chain of standard configuration and custom ABAP exits before the document is saved. This registry is the single map of every mechanism that does that rewriting, so the next agent or analyst does not re-derive it from scratch. If one of these is wrong, postings land in the wrong segment, payments mis-route, or the audit trail goes blank.

PRIMARY EXIT POOL

YRGGBS00

The global FI form pool (tx GGB0/GGB1). Hosts ~13 UNESCO exits across two families: BA/Fund/CC derivation and XREF office-tagging. Registered in T080D.

BUSINESS-AREA ENGINE

BASU · YFI_BASU_MOD

No-transport BA substitution. YTFI_BA_SUBST (modern, ranges) + YBASUBST (legacy, flat) read by class YCL_FI_ACCOUNT_SUBST_READ from Form U910.

PAYMENT GATES

BCM / WS90000003

FI Release-for-Payment custom tasks (YBSEG_REL, direct UPDATE bseg) + the BCM reject BAdI. Signatory selection itself is 100% standard.

BASU — Business-Area substitution engine

UNESCO maintains complex BA derivation without raising a transport: tx YFI_BASU_MOD (program YFI_ACCOUNT_SUBSTITUTION) edits range tables read at runtime by YCL_FI_ACCOUNT_SUBST_READ, called from YRGGBS00 Form U910. This is the "hidden" substitution layer that lets non-ABAPers manage rules the transport-locked GGB1 config can't.

Config drift (claim 169): NTB01-USD02 carries a PFF entry in YBASUBST but every real posting lands GEF — because Step 010 (U904) overrides U910 on the cash side. Reading the config table alone gives a false BA; verify against posted BSEG.

The EBS third actor — YTBAM001

On bank-statement postings the same YCL_FI_ACCOUNT_SUBST_READ is also called earlier, from custom code YTBAM001 (CMOD YTFBE001 → enhancement FEB00001 → EXIT_RFEBBU10_001 → include ZXF01U01, active since 2001). It sets E_FEBEP-GSBER during FEBEP→BSEG conversion. Gated by EFART='E' AND BUKRS IN {UBO, IIEP, UNES}.

XREF office-tagging trio — UXR1 / UXR2 / UZLS

An independent mechanism from BA/Fund derivation: it stamps the posting user's office code onto the document and uses it to route the payment. Reads USR05.PARID='Y_USERFO' (SU3 user parameter), validates against custom table YFO_CODES. The defect class behind INC-000005240.

005
UXR1 → writes BSEG.XREF1 from USR05.Y_USERFO. guard commented out — overwrites even user-typed values. Non-blocking warning w018 if not in YFO_CODES.
006
UXR2 → writes BSEG.XREF2 only when blank. Asymmetric.
007
UZLS → reads XREF2, derives BSEG.ZLSCH (payment method) per company code.

The critical asymmetry in UXR2 (real source)

IF bseg_xref2 = space.              " user did not type anything
    SELECT SINGLE * FROM usr05 WHERE bname=sy-uname AND parid='Y_USERFO'.
    IF sy-subrc IS INITIAL.
        bseg_xref2 = usr05-parva.   " ← auto-write, NO validation
    ENDIF.
ELSE.                               " user typed a value
    SELECT SINGLE * FROM yfo_codes WHERE focod = bseg_xref2.
    IF sy-subrc <> 0.
        MESSAGE e018(zfi) WITH bseg_xref2.  " ← HARD error, stops posting
    ENDIF.
ENDIF.
Why INC-000005240 happened: the SPACE branch trusts USR05 blindly (no YFO_CODES check). A wrong Y_USERFO='HQ' in user master is written to XREF2 with no validation. F-53 hides XREF2 on screen → UXR2 always takes the SPACE branch → AL_JONATHAN's Jakarta postings were silently tagged HQ instead of JAK, and UZLS then mis-routed the payment method.

BCM / Payment workflow custom code

Surfaced by the BCM-signature analysis and promoted to the registry (Section 13) on 2026-06-20. Scope note: the signatory/agent selection is 100% standard SAP (RH_GET_ACTORS). The custom code lives in a separate gate — FI "Release for Payment" (WS90000003, document-level, before F110) — and in the BCM reject path. It blocks/reverses documents; it does not decide who signs.

The YXUSER backdoor — the "open door"

Several of the most restrictive force-mapping routines in YRGGBS00 (the Asset ones) start with a check against custom table YXUSER. If the posting user is registered there with the matching XTYPE, the entire routine is skipped — the fund/cost-center force-map and the WBS clear do not apply.

SELECT SINGLE * FROM yxuser
  WHERE xtype = 'AF'   " or 'AA'
    AND uname = sy-uname.
CHECK sy-subrc <> 0.   " if user FOUND (subrc=0) → SKIP the whole routine
XTYPEBypassesEffect of an entry
AFUAEP (assets expenses)Post asset expenses without the mandatory Fund/CC force-map
AAUATF / NSAI (assets technical)Post technical asset docs without clearing the WBS element
Audit risk: any user a functional admin adds to YXUSER can bypass the hardcoded fiscal-year and fund-center guardrails. Likely used for batch/interface IDs and migration tools, but it is an un-gated exception list that must be monitored to know who can post non-standard account assignments.
