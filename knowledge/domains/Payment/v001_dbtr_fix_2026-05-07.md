### UNESCO canonical pattern for paying-co structured address — production CGI tree

Per `dmee_tree_node_p01.csv` (CGI tree `/CGI_XML_CT_UNESCO`), Dbtr structured-address leaves are wired with `EXIT_FUNC = FI_CGI_DMEE_EXIT_W_BADI` and dispatch to BAdI implementation `YCL_IDFI_CGI_DMEE_FALLBACK_CM001` method `GET_CREDIT` (which despite the name handles BOTH credit and debit branches per `FLT_VAL_DEBIT_OR_CREDIT` filter).

CGI Dbtr leaves with this pattern (TIER_1 production):
- StrtNm: lines 808 / 895 / 1008 (TAB/FLD empty → BAdI provides value)
- BldgNb: lines 1018 / 1056
- PstCd: lines 829 / 878 (with `FPAYH/ZPSTL` fallback)
- TwnNm: lines 809 / 893 (with `FPAYH/ZORT1` fallback)
- Ctry: lines 797 / 830 / 1416

The BAdI method dispatches on `i_node_path` (full XML path string) and reads master data via `T001(i_fpayh-zbukr).ADRNR → ADRC.STREET / HOUSE_NUM1 / POST_CODE1 / CITY1`.

### BAdI extension — ABAP delta

Edit `YCL_IDFI_CGI_DMEE_FALLBACK_CM001` method `GET_CREDIT`, add cases:

```abap
WHEN '<PmtInf><Dbtr><PstlAdr><StrtNm>'.
  SELECT SINGLE adrnr INTO @DATA(lv_adrnr) FROM t001 WHERE bukrs = @i_fpayh-zbukr.
  IF lv_adrnr IS NOT INITIAL.
    SELECT SINGLE street, house_num1 INTO @(DATA(ls_a)) FROM adrc WHERE addrnumber = @lv_adrnr.
    CONCATENATE ls_a-street ls_a-house_num1 INTO c_value SEPARATED BY space.
    CONDENSE c_value.
  ENDIF.

WHEN '<PmtInf><Dbtr><PstlAdr><PstCd>'.
  SELECT SINGLE adrnr INTO @DATA(lv_adrnr) FROM t001 WHERE bukrs = @i_fpayh-zbukr.
  IF lv_adrnr IS NOT INITIAL.
    SELECT SINGLE post_code1 INTO @c_value FROM adrc WHERE addrnumber = @lv_adrnr.
  ENDIF.
```

Pattern A guard (3-line `IF c_value IS INITIAL ... ENDIF`) preserved at end of method.

### Why revisions #1 and #2 were wrong (postmortem)

| Revision | What was proposed | Why it was wrong |
|---|---|---|
| #1 (Fix 1/2 below) | Bind StrtNm to FPAYHX/REF01 + register CM005 in OBPM3 | REF01 is CGI/CITI byte buffer populated by CM005 GENERIC; SEPA tree doesn't use REF01 architecture. Forcing CM005 onto SEPA via OBPM3 would work but is unnecessary cross-format coupling. |
| #2 (above) | Bind StrtNm to FPAYHX/ZPFST etc. (claimed "paying-co Z-ext") | ZPFST/ZPLOR/ZLISO are **VENDOR-context** per production V000 (already used under Cdtr/PstlAdr N_4754354180). Field text "Payee" = recipient = vendor. Binding Dbtr to ZPFST would render vendor address, same bug as ZSTRA. |
| #3 (current) | EXIT_FUNC=FI_CGI_DMEE_EXIT_W_BADI for StrtNm/PstCd; FPAYHX/ORT1Z + LAND1 for TwnNm/Ctry | Mirrors UNESCO production CGI tree pattern verified in `dmee_tree_node_p01.csv`; BAdI extension is the only path to paying-co STREET/POSTCODE since FPAYHX has no such fields. |

The methodological lesson: **each revision read more production evidence (Note XML → DDIF FPAYHX catalog → V000 P01 actual bindings)**. Revision #3 uses the highest-evidence layer (production V000 active tree) and matches UNESCO's canonical paying-co pattern (CGI tree).

New brain rule (session #71): **`feedback_dmee_validate_node_context_dbtr_vs_cdtr_before_binding`** — Before binding a DMEE leaf to any FPAYHX field, walk the tree from the leaf's NODE_ID up to the nearest `Dbtr/Cdtr/UltmtDbtr/UltmtCdtr/InitgPty` ancestor to confirm the context. UNESCO field naming convention with `Z*` prefix on FPAYHX does NOT signal paying-co — those Z-extensions can be either context. Production V000 active version is the authoritative source for who-binds-to-what.

## Root cause analysis

### Issue 1 — Dbtr `<StrtNm>` renders vendor street, not UNESCO HQ

**Design assumption (incorrect)**: `FPAYH-ZSTRA` is populated by F110 with paying co address for Dbtr-context leaf rendering.

**Actual F110 runtime behavior**: `FPAYH-ZSTRA` is populated with **vendor address** (per-line, REGUH-ZSTRA propagates to FPAYH-ZSTRA). Same field reads vendor data regardless of XML context (Dbtr or Cdtr).

**Why design assumption failed**:
- ICTP tree (`/SEPA_CT_ICTP_ISO`) Dbtr StrtNm uses `FPAYH-ZSTRA` — but ICTP context might be different (maybe single-vendor scenarios where ZSTRA happens to match)
- REGUH RFC extract showed ZSTRA values for vendor — we extrapolated to mean "Z-include populates ZSTRA contextually" — but actual F110 logic populates FPAYH-ZSTRA with vendor address always (per-line scope)

**Evidence — XML output 2026-05-07**:
```
FPAYH-ZSTRA value = "BFM/FAS/PAY"
ADRC.STREET (UNESCO HQ) = "Place de Fontenoy"
ADRC.STREET (BERTOLDINI) = "BFM/FAS/PAY"
```
The XML rendered "BFM/FAS/PAY" → confirms FPAYH-ZSTRA = vendor address at runtime.

### Issue 2 — `<BldgNb>` + `<PstCd>` missing

**Design**: Source `FPAYHX/REF01[100..110]` (BldgNb) and `FPAYHX/REF01[80..90]` (PstCd). Both depend on CM005 GENERIC FM populating `FPAYHX-REF01` byte buffer per claim 105 brain layout:
- `REF01[0..60]` = ADRC.STREET
- `REF01[60..80]` = ADRC.BUILDING
- `REF01[80..90]` = ADRC.POST_CODE1
- `REF01[100..110]` = ADRC.HOUSE_NUM1

**Actual runtime**: `FPAYHX-REF01` is **EMPTY** in F110 V01T output. Empty-suppress conditions correctly fire → BldgNb and PstCd suppressed → no XML render.

**Root cause**: CM005 GENERIC (`FI_PAYMEDIUM_DMEE_CGI_05`) is NOT registered for /SEPA_CT_UNES Event 05 in OBPM3. Without this registration, Event 05 firing default does NOT include CM005 → REF01 buffer not populated.

**Brain claim 105 said "CM005 fires automatically at every Event 05 call"** — but only if registered for the format. SEPA tree never had this registration; ICTP tree apparently doesn't either, but ICTP renders PstCd anyway via different mechanism (we couldn't trace exact path without ICTP F110 output).

## Lessons learned — brain rule update

### Discovery method retrospective

| Method used | Pre-test claim | Empirical result | Conclusion |
|-------------|----------------|------------------|-----------|
| RFC extract REGUH-ZSTRA | Vendor data populated | Vendor data populated ✓ | True but irrelevant for Dbtr |
| RFC extract ADRC UNESCO HQ | "Place de Fontenoy / 7 / 75007 / PARIS / FR" | Confirmed | True at master data layer |
| Brain claim 105 (CM005 byte layout) | "CM005 fires automatic at Event 05" | CM005 did NOT fire for SEPA | False without OBPM3 register |
| ICTP tree pattern mirror | "ICTP uses FPAYH-ZSTRA for Dbtr" | ICTP context might differ | Unverifiable without ICTP F110 output |
| **F110 + SAPFPAYM_MERGE empirical XML** | (skip — REGUH evidence enough) | **Caught design flaw** | **CRITICAL — only definitive validation** |

### New brain feedback rule

**`feedback_v001_dmee_design_requires_empirical_xml_output_test`** (severity: CRITICAL)

> When designing DMEE V001 changes for production deployment, the ONLY definitive validation is an empirical XML output test from F110 + SAPFPAYM in a real environment (D01 dev minimum). RFC table extracts (REGUH/ADRC), brain claims about buffer populating mechanisms, and pattern-mirror reasoning across DMEE trees are NECESSARY but NOT SUFFICIENT. The runtime context binding (which field maps to which XML scope) cannot be predicted from static analysis alone.
>
> **Why**: Session #2026-05-07 V001 SEPA Dbtr design flaw — `FPAYH-ZSTRA` was assumed to populate UNESCO HQ paying co address based on REGUH-ZSTRA semantics. F110 runtime actually populated FPAYH-ZSTRA with vendor address regardless of XML context. RFC extracts showed correct vendor data → led to false confidence. Empirical XML output (collector 10002B 2026-05-07) showed `<StrtNm>BFM/FAS/PAY</StrtNm>` instead of expected `<StrtNm>Place de Fontenoy</StrtNm>` — vendor address contaminated Dbtr context.
>
> **How to apply**: Before any V001 transport release, perform F110 + SAPFPAYM_MERGE end-to-end test in D01 (or equivalent dev system) and verify XML output matches expected for each PstlAdr leaf. If D01 has BCM cross-payment-run setup blocking direct medium creation, use SAPFPAYM_MERGE bypass + access output via `\\hq-sapitf\SWIFT$\D01\INPUT\`. Skip-empirical paths (REGUH analysis, brain claims) are valid for hypothesis but NEVER for design closure.
